# 01 项目总览与业务介绍

## 一、项目定位

**SuSuMonitor 是一套"前后端 + Agent"全栈的 Linux 服务器监控平台**,主题采用涂山苏苏(狐妖小红娘)IP 形象,仅供内部学习与 demo 用途。

核心价值:让运维人员通过一个 Web 控制台,**实时查看多台服务器的 CPU/内存/磁盘/网络指标、配置告警规则、并直接打开 Web 终端操作服务器**,而无需登录每台机器。

### 三端架构(一句话)

```
┌─────────────┐   REST / WebSocket    ┌──────────────────┐    WebSocket(出站)    ┌─────────────┐
│  Vue3 前端   │ ◄───────────────────► │  Java 后端(核心)   │ ◄───────────────────► │  Go Agent   │
│  Web 控制台  │   /api + /ws/monitor  │  Spring Boot      │    /ws/agent          │  采集+终端   │
└─────────────┘                       └──────────────────┘                       └─────────────┘
                                          │ MySQL + RabbitMQ
```

- **Go Agent**:部署在每台被监控服务器上的轻量采集器,主动出站连接后端(被监控机不需要公网 IP、不需要开放入站端口),采集指标、承载 Web 终端(PTY)。
- **Java 后端**:认证授权、服务器资产管理、指标接收与存储、告警评估、终端中继路由、WebSocket 双通道。
- **Vue 前端**:登录注册、Dashboard、服务器列表/详情、实时指标、告警记录/规则、Web 终端、用户审核。

### 技术关键词(详见 02 文档)

Java 21 / Spring Boot 3.4.7 / MyBatis / MySQL 8.4 / RabbitMQ / WebSocket / JWT / AES-256-GCM / sshj / Flyway;Go 1.23 / gopsutil / coder-websocket / creack-pty;Vue 3.5 / TypeScript / Pinia / Element Plus / Vite / Vitest / xterm.js / ECharts(声明未用)。

## 二、五大业务模块与业务逻辑

### 业务 1:用户认证与管理员审核

**业务逻辑**:系统面向"管理员 + 普通用户"两类角色,所有用户必须先注册、管理员审核通过后才能使用监控功能。

| 环节 | 业务规则 |
|---|---|
| 注册 | 用户名唯一;**第一个注册的用户自动成为管理员**(空库场景);后续用户均为 `pending` 待审核状态,密码 BCrypt 哈希存储 |
| 登录 | 校验用户名/密码;仅 `approved` 用户可登录;签发 JWT(默认 72 小时);**用户不存在时也执行一次 BCrypt 比较**(dummy hash),防用户名枚举时序攻击 |
| 审核 | 管理员查看待审核列表,approve/reject;拒绝后该用户 token 即使未过期也立即失效(过滤器每请求回查数据库审核状态) |
| 登出 | 无状态登出,客户端删除 token |

**并发难点**:空库时两个用户同时注册,如何保证只有一个首管理员?
→ `SELECT ... FOR UPDATE` 行锁锁住 `auth_bootstrap_state` 单例表行 + 条件更新(`WHERE admin_initialized=0`)+ 数据库唯一索引,三重保障"最多一个首管理员"。

### 业务 2:服务器资产管理(CRUD + SSH 安全)

**业务逻辑**:管理员录入服务器(主机、端口、认证方式、SSH 凭据),系统提供增删改查,删除为**软删除**;录入后必须先完成 **SSH 主机指纹确认** 才能执行 SSH 测试。

| 环节 | 业务规则 |
|---|---|
| 创建 | 认证方式二选一:密码(必须有密码)或私钥(可带 passphrase);SSH 凭据用 **AES-256-GCM 加密**后入库,密文通过 AAD 绑定服务器 ID 与凭据类型 |
| 列表/详情 | 只读字段不返回任何凭据列;支持白名单排序(防 SQL 注入);分页 |
| 更新 | 全量 PUT;凭据留空=保留旧值;**修改 host/port 后自动清空已确认的主机指纹**(目标变了必须重新确认,防止中间人) |
| 删除 | 软删除:置 `deleted=1` + 写入 `delete_token` 释放 host 唯一约束;已删除记录不再出现在任何查询 |
| SSH 测试 | 要求指纹已确认;测试前重新查库比对 8 个字段(防 TOCTOU:测试期间凭据被改);**指纹验证通过后才解密凭据**;失败分类:50002 连接失败 / 50003 认证失败 / 50400 超时 / 42900 并发超限 |
| 主机指纹 | 只接受 `SHA256:` 格式;首次确认与轮换通过 `compareAndSet`(带旧指纹做 CAS 条件)原子写入,防并发轮换 |

**SSRF 防护**:SSH 出站目标必须是端口白名单 + CIDR 白名单内的地址;解析 DNS 后逐个校验每个 IP,拒绝任意地址/组播/链路本地/云元数据地址(169.254.169.254 等)。

### 业务 3:实时指标监控(核心链路)

**业务逻辑**:Agent 每 5 秒采集一次服务器指标,通过 WebSocket 上报,后端校验落库,并把最新指标**实时推送给正在查看该服务器的浏览器**。

完整链路:

```
Go Agent(gopsutil 采集 CPU/内存/磁盘/网络/温度/负载)
   │ 每 5s,metrics.report 消息(UUID message_id + UTC collected_at)
   ▼
Java /ws/agent 通道(限流 → UUID 校验 → 服务器归属校验)
   ▼
MetricsService.report():
   ① FOR UPDATE 锁服务器行(串行化)
   ② 幂等:metrics_ingestions 唯一键,重复 message_id 静默丢弃
   ③ 乱序拒绝:collected_at 不严格递增则拒绝(40002)
   ④ 写 metrics 宽表 + 同事务写 message_outbox(Outbox 模式)
   ▼
事务提交后(AFTER_COMMIT):
   ① 浏览器收到 metrics.update 实时推送
   ② Outbox 发布器轮询(200ms)把事件可靠投递到 RabbitMQ
   ▼
Alert 消费者评估告警规则 → 命中则 alert.push 推浏览器 + 状态机管理
```

**关键可靠性设计**:
- 指标入库与 outbox 事件**同事务**:入库必有事件,不会"数据到了消息丢了"。
- 重复上报(网络重发)靠 `message_id` 幂等,不乱序覆盖靠行锁 + `collected_at` 严格递增。
- 指标保留 10 天,每天 03:00 分批清理(每批 1000 条独立事务,AtomicBoolean 防重叠)。

### 业务 4:告警管理

**业务逻辑**:管理员为服务器配置告警规则(如"CPU > 90% 持续报警"),后端消费指标事件,越界触发告警记录并通过 WebSocket 实时推送;恢复后自动标记已解决。

| 规则 | 说明 |
|---|---|
| 指标 | cpu / memory / disk / temperature / load |
| 运算符 | `> >= < <=`(BigDecimal 比较,2.0 == 2.00) |
| 等级 | warning / critical |
| 作用域 | 可绑定具体服务器,也可建通用规则(所有服务器生效) |
| 唯一性 | `(server_id, metric, operator, threshold, level)` 五元组查重 + 数据库生成列唯一索引双保险;软删除后允许重建 |

**告警状态机**(`AlertStateMachine`,纯逻辑无 DB 依赖):

```
无状态行(首次越界)  → Trigger(建记录+建状态行+推送)
状态 active + 越界  → Continue(仅刷新时间,**不重复建记录** → 防告警风暴)
状态 active + 恢复  → Resolve(记录置已解决 + **物理删除状态行**)
```

> ⚠️ 注意:恢复必须是"删除状态行"而不是"置 active=0"——置 0 会导致恢复后再次越界永远不触发(真实 Bug,详见 05 文档)。

**消费侧(MVP-11)**:告警评估从本地事务事件迁移到 RabbitMQ 消息驱动——`AlertMessageConsumer` 幂等消费 `metrics.reported.v1`(consumer+event_id 唯一键),业务事务成功才 ACK,可重试错误指数退避 3 次,不可重试数据错误直接进 DLQ。

### 业务 5:Web 终端(Web SSH,PTY 中继)

**业务逻辑**:用户在浏览器里打开一个 xterm.js 终端,输入命令,实时看到输出——就像 SSH 登录了服务器一样。实现方式是**浏览器 → Java 中继 → Go Agent 上的 Linux PTY(伪终端)**。

```
浏览器 xterm.js
   │ terminal.open / input / resize / close
   ▼
Java /ws/monitor(限流 + 鉴权 + 会话元数据管理,不存任何终端内容)
   │ 注入服务端生成的 session_id / server_id
   ▼
Java → Agent /ws/agent 通道(中继注册表路由)
   ▼
Go Agent:creack/pty 启动 /bin/bash 伪终端
   │ 输出经 Base64 + 字节级令牌桶限流回传
   ▼
浏览器实时回显
```

| 设计点 | 方案 |
|---|---|
| 会话模型 | 每用户每服务器配额(用户 2 / 服务器 4 / 全局 16),`(user_id, open_message_id)` 幂等 |
| 内容安全 | **Java 端不持久化任何终端内容**,只存元数据;三方共享协议校验器(40003 非法载荷) |
| 带宽保护 | 输出 256KB/s 令牌桶,超限直接服务端关闭会话(`output_rate_exceeded`),防止慢消费者拖垮 |
| 慢消费者 | 浏览器收不过来 → 背压检测(5s 发送超时 / 256KB 缓冲溢出)→ 关会话 + 移除订阅 + 1011 关闭 |
| 断连收口 | 浏览器断 → 通知 Agent 关 PTY;Agent 断 → 所有会话标 error;kill 进程组保证无孤儿 shell |
| 会话过期 | 空闲 20 分钟 / 总寿命 8 小时,每小时定时清理 |

**Agent 模式与 SSH 测试的区别**:SSH 测试是"后端主动连服务器"(要求后端可达服务器);Agent 模式是"Agent 主动连后端"(家庭内网也适用),Web 终端走后者。

## 四、业务闭环总览(面试讲述顺序)

1. 用户注册 → 首管理员 / 等待审核
2. 管理员审核通过
3. 管理员录入服务器 + 确认 SSH 指纹(可选,Agent 模式可跳过)
4. 管理员为服务器生成 Agent Token(明文仅返回一次)
5. 在目标服务器部署 Go Agent(环境变量配 token,一键脚本安装)
6. Agent 出站连接后端 → 认证 → 心跳 → 每 5s 上报指标
7. 前端实时看到指标曲线 + 在线状态
8. 管理员配置告警规则 → 指标越界 → 记录 + 实时推送
9. 恢复 → 自动解决;列表/详情随时查看历史
10. 需要操作时打开 Web 终端,直接执行命令

这个闭环覆盖了从"发现机器"到"监控"再到"处置"的完整运维场景。
