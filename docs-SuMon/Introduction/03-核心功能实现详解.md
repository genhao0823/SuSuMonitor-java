# 03 核心功能实现详解

> 本文按功能逐个拆解实现原理,对应代码路径均标注。建议面试时能对每个功能讲出:**入口 → 校验 → 核心逻辑 → 事务/并发处理 → 出站推送 → 失败兜底** 这条线。

## 功能一:认证与授权(JWT + BCrypt + 每请求回查)

**涉及**:`module/auth/*`、`security/JwtTokenServiceImpl`、`security/JwtAuthenticationFilter`、`security/SecurityConfig`、`config/JwtKeyConfig`

### 1. 注册与首管理员(并发安全)

```
POST /api/auth/register
 1. 用户名查重 → 冲突抛 40900
 2. SELECT ... FOR UPDATE 锁 auth_bootstrap_state 单例行(锁持续到事务结束)
 3. adminInitialized=false → 该用户 role=admin + approved;否则 role=user + pending
 4. BCrypt 哈希密码(Spring Security PasswordEncoder)
 5. 插入用户;DuplicateKeyException → 40900(唯一索引是并发注册最终防线)
 6. 首用户场景:UPDATE auth_bootstrap_state SET admin_initialized=1 WHERE admin_initialized=0
    (0 行受影响 → 说明并发下已被别人抢注 → DATABASE_ERROR 回滚)
 7. @Transactional 整体包裹,任一步失败全回滚
```

> 面试点:**三重保障** = 行锁(串行化)+ 条件更新(幂等边界)+ 唯一索引(兜底)。

### 2. 登录与防枚举攻击

- 用户不存在时,用**预计算的 dummy BCrypt hash** 参与 `matches()`,让"用户不存在"与"密码错误"耗时一致,防时序侧信道枚举用户名。
- 校验 `review_status=approved` 与角色合法,否则 403。
- 签发 JWT:`iss=susumonitor / aud=susumonitor-api / sub=userId / username / iat / exp(72h) / jti(UUID)`,HS256。
- 响应 `Cache-Control: no-store` 防 token 缓存。

### 3. JWT 校验与"即时失效"

`JwtAuthenticationFilter`(OncePerRequestFilter,注册在 UsernamePasswordAuthenticationFilter 之前,FilterRegistrationBean 防重复注册):

1. `shouldNotFilter` 放过 health/ready/register/login(过期 token 不阻塞公开接口)。
2. 有 Authorization 头 → 必须验证成功,否则 401;验签固定要求 HS256、iss/aud 匹配、clockSkew 30s。
3. **验签后回查数据库最新状态**(selectAuthenticationUserById,不含密码哈希):review_status=approved、角色合法、username 与库一致 —— **管理员拒绝审核/改角色,该用户 token 立即失效**,不需要等过期。
4. SecurityContext 放入 `AuthenticatedUser` record,authority=`ROLE_<role>`。

SecurityConfig:CSRF/formLogin/logout 全禁用,STATELESS;公开面:health/ready/register/login/两个 WS 通道(WS 自鉴权);`/api/admin/**`、服务器写操作、agent/**、ssh/**、告警规则写 → `hasRole("ADMIN")`。

### 4. AES-256-GCM 凭据加密(CredentialCipher)

```
信封格式: v1:<Base64(12B 随机IV + GCM密文含128b tag)>
AAD = "susumonitor:server:{serverId}:credential:{credentialType}"
AAD 白名单类型: ssh_password / ssh_private_key / ssh_private_key_passphrase
```

- 密钥 32 字节(Base64 解码后恰好 32 字节,启动期 fail-fast),从环境变量 `AES_GCM_KEY` 注入,不硬编码。
- **AAD 绑定上下文**:密文只能在"同一服务器 ID + 同一凭据类型"下解密;换库/换行/跨类型解密必失败。
- 解密失败抛 IllegalStateException → 上层转 50000,不泄露明文。

## 功能二:服务器管理 + SSH 安全

**涉及**:`module/server/*`、`ssh/SshConnectionTester`、`ssh/SshOutboundPolicy`

### 1. 创建时的凭据处理顺序(注意这个细节)

```
@Transactional:
 1. insertServerBase 回填自增 ID
 2. 用新 ID 作为 AAD 上下文加密凭据
 3. updateCredentialCiphertexts 写回密文
```

认证方式组合校验:password 认证必须有且只有 ssh_password;private_key 认证必须有私钥、可带 passphrase、不能带密码。

### 2. 更新与软删除

- **更新(PUT 全量)**:取旧密文;同认证方式 + 凭据为 null → 保留旧密文;切换认证方式 → 清空另一套;**仅当 ssh_host/ssh_port 不变才保留已确认指纹,否则置 NULL**(目标变更必须重新确认指纹,防中间人)。
- **删除(软删除)**:`SET deleted=1, delete_token=UUID()`;条件 `WHERE deleted=0` 保证幂等(更新 0 行 → 40400);delete_token 释放 host 唯一约束(同 host 可重建)。

### 3. SSH 主机指纹流程(ServerSshServiceImpl.updateHostKey)

```
1. 格式校验:^SHA256:[A-Za-z0-9+/]{43}$(拒绝 MD5/SHA-1)
2. 首次确认不允许 replace=true;已有指纹且不匹配且未声明 replace → 40902
3. connectionTester.verifyHostKey(host, port, expected) —— 只握手核对指纹,不传凭据
4. 指纹匹配还需比对算法一致
5. compareAndSetSshHostKey:(serverId, ssh_host, ssh_port, previousFingerprint) 为 CAS 条件
   —— 0 行 → 40400 或 40900(并发轮换冲突)
```

### 4. SSH 测试(ssh/test)与 TOCTOU 防护

```
1. 请求体必须为空(传 body → 40002)
2. 要求指纹已确认 → 否则 40901
3. assertSshSnapshotCurrent:重新查库比对 8 个字段,测试期间被改 → 40900
4. 凭据以 Supplier 惰性提供 —— 仅在指纹验证通过后才解密
5. 密码/passphrase 用 char[] 并在 finally 中抹零(PasswordUtils.blankOut)
6. sshj 执行:
   - 虚拟线程执行器(Executors.newVirtualThreadPerTaskExecutor)+ future.get(总超时)
   - 超时置 cancelled 标志 + future.cancel(true) + 关闭活动 SSHClient
   - Semaphore(maxConcurrentConnections=8) tryAcquire 失败 → 42900
7. 错误分类:UserAuthException → 50003(认证失败);
   连接阶段 IOException → 50002(连接失败);超时 → 50400
```

**指纹计算细节**:`CapturingHostKeyVerifier.verify()` 内用 `KeyType.fromKey` 取算法,按 OpenSSH 公钥 blob 自算 SHA-256 指纹(`Buffer.PlainBuffer().putPublicKey()` + Base64URL),同时用 sshj 的 FingerprintVerifier 校验;观察到公钥但算法/指纹不匹配 → 40902。

**SSRF 防护(SshOutboundPolicy)**:
- 端口白名单 + CIDR 白名单(自实现 IPv4/IPv6 CidrRange,只接受数字地址,避免 DNS 解析混淆)。
- `resolveAndValidate`:解析 DNS 后**逐个校验每个 IP**,拒绝 anyLocal/multicast/link-local 及云元数据地址(169.254.169.254 等 5 个),解析数量上限 8 → 违规 40301。

### 5. Agent Token 生命周期

- 生成:32 字节 SecureRandom → Base64URL,明文**只返回一次**;库中只存 `sha256:<hex>`。
- 三个接口:register(要求当前无 token)/ rotate(要求已有)/ revoke(要求未撤销,同时置 agent_status=offline)。
- 认证比对:`MessageDigest.isEqual` 常量时间比较哈希。
- 旋转/撤销后旧连接通过心跳机制(乐观锁)自动失效,前端服务器详情页的 AgentTokenDialog 封装。

## 功能三:指标链路(采集 → 上报 → 幂等落库 → 实时推送 → 可靠发布)

**涉及**:`agent-go-SuMon/internal/{collector,reporter,wsclient}`、`module/metrics/*`、`websocket/MonitorMetricsPublisher`、`metrics/outbox/*`

### 1. Agent 采集(GopsutilCollector)

| 指标 | 采集方式 |
|---|---|
| CPU 使用率 | `cpu.Percent(1s, false)` 取整体值(1 秒采样窗口) |
| 内存 | `mem.VirtualMemory()` → used_percent/used/total |
| 磁盘 | `disk.Usage(systemDiskPath())`(Windows C: / 其他 /) |
| 网络 | `net.IOCounters(false)` 所有网卡合计 rx/tx |
| 温度/负载 | 可选:`host.SensorsTemperatures()` / `load.Avg()`;失败置 nil 不影响其他指标 |

- 数值统一保留两位小数;`Collector` 接口化,字段可注入(测试替身友好)。
- 采集周期默认 5s(`SUSUMONITOR_COLLECT_INTERVAL_SECONDS`);采集/上报失败只 Warn,**Agent 不退出**(best-effort)。

### 2. Agent 上报与重连(wsclient)

```
Run() 主循环状态机:Disconnected → Connecting → Authenticating → Connected → Reconnecting
- 首帧 agent.authenticate{server_id, token}(不走 HTTP Header,防日志泄露)
- 心跳 goroutine 每 30s 发 heartbeat(可携带投递遥测);接收 goroutine 每 95s 读超时(略大于后端 90s 判定)
- 指数退避:5s → 10s → 20s → 40s → 60s 封顶,每次认证成功后退避重置为 5s
- equal jitter:实际等待 = backoff/2 + rand(backoff/2),防多 Agent 惊群
- 终态错误不重连:context 取消 / 服务端返回 40100 错误帧(token 被撤销)
- 优雅退出:SIGINT/SIGTERM → context 取消 → WS 关闭 → CloseAll 清 PTY 会话
```

**可靠投递管线(reporter + metricbuffer,2026-08-05 M1-M4)**:

```
采集 → reporter.Report:完整 metrics.report 帧(UUID)先持久化入本地 FIFO,再发送
  → 同一时刻仅一条 in-flight(保 collected_at 严格递增)
  → metrics.ack 且 message_id 匹配队首 → 原子删除并(有积压时)按最小间隔发下一条
  → ACK 超时 → 指数退避 + equal jitter 重传原 UUID 完整帧(不删队首)
  → metrics.nack 且 message_id 匹配队首 → 移入本地死信(snapshot v2,与队列共用容量上限,超限丢最旧)
  → 泛化 error 帧 → 不触碰队首
  → 缓冲满 → 拒绝最新采样并计数(drop),保留最旧 FIFO 前缀
  → 心跳携带 Stats()(pending/bytes、oldest、drop、dead-letter)→ Server 落库展示
```

### 3. 后端接收(幂等 + 乱序拒绝,`MetricsServiceImpl.report`)

```
1. 校验:messageId 必须 UUID;payload.server_id 必须等于会话认证的服务器;
   collected_at 不能晚于当前 +5min;百分比 0~100;used ≤ total
2. SELECT ... FOR UPDATE 锁服务器行 —— "重复判定 + 乱序判定 + 写入"在同一服务器内串行
3. 幂等:insert metrics_ingestions(server_id, message_id) 唯一键冲突 → 静默返回
   (重复投递不产生第二次业务效果,也不重复推送)
4. 乱序:MAX(collected_at) 严格小于新值才接受,否则抛 MetricsRejectedException
   → 回 correlated metrics.nack(reason=stale_collected_at,code=40002,不落库不发事件)
5. 写 metrics 行 + enqueue message_outbox(同事务)+ 发布本地事件
```

**可靠确认/拒绝语义(2026-08-05,M4)**:事务成功回 `metrics.ack`(原 message_id),Agent 才删本地 FIFO 队首;可关联且永久无效的指标(载荷非法 / 乱序 / 服务器不存在)回 `metrics.nack`(reason 分别为 `invalid_metrics_payload` / `stale_collected_at` / `server_not_found`),Agent 将队首移入本地持久化死信(snapshot v2)且不重试;不确定或瞬时失败(DB、内部、限流)只回泛化 `error`,**不删队首**。Agent 心跳携带投递遥测(pending count/bytes、最旧采样、丢弃计数、死信条数/字节),Server 落库 `servers.delivery_*`(V19)并经 `GET /api/servers/{id}/status` 返回,服务器详情页展示。

### 4. 事务后推送(AFTER_COMMIT)

`MonitorMetricsPublisher` 用 `@TransactionalEventListener(phase = AFTER_COMMIT)` 监听 `MetricsReportedEvent`:
- 事务**提交成功** → 向订阅了该 server_id 的 Monitor 会话广播 `metrics.update`;
- 事务回滚 → 事件自动丢弃,浏览器不会看到假数据。

> 面试点:为什么用 AFTER_COMMIT 而不是同步推送?因为监听器执行时事务可能未提交,此时广播的指标在崩溃场景下可能"推送了但没落库";AFTER_COMMIT 保证"推的都是已提交数据"。

### 5. Outbox 可靠发布(Transactional Outbox 模式)

```
指标事务内:  INSERT metrics + INSERT message_outbox(event_id, status='pending')
   ▲ 同事务,要么都提交要么都回滚 —— 入库必有待发布事件
发布器(OutboxPublisherScheduler,fixedDelay=200ms):
  SELECT ... FOR UPDATE SKIP LOCKED 取 pending 行(多实例/重叠调度不重复取)
  → rabbitTemplate.convertAndSend(带 CorrelationData,mandatory=true)
  → 同步等待 Publisher Confirm(CORRELATED)
  → ack:markPublished(WHERE status='pending' 条件更新)
  → nack/超时/异常:markRetry(attempts+1,next_attempt_at = now + min(2^attempts, 300s))
  → 单行失败不中断本轮其余行
```

- **发布侧无失败上限**:Outbox 语义要求 Broker 恢复后必补发,与消费侧 DLQ 分离。
- **至少一次**:Confirm 超时但消息已到 Broker 时重发同一 event_id,消费侧幂等兜底。
- 关键修复:时间比较必须 `UTC_TIMESTAMP()` 而非 `NOW()`(会话时区东八区导致退避永不算到期,见 05 文档)。
- 轮询 1000ms → 200ms 后告警推送延迟 p50 835→242ms(-71%)。

### 6. 查询与清理

- `latest`:`ORDER BY collected_at DESC, id DESC LIMIT 1`,无记录 40400。
- `history`:时间窗口 ≤7 天 + 分页 ≤100。
- 清理:每天 03:00,`(collected_at, id)` 顺序每批 1000 条、最多 100 批,每批独立 TransactionTemplate 事务,AtomicBoolean CAS 防重叠,删 0 行即停。

## 功能四:告警系统(规则 + 状态机 + 消息驱动评估)

**涉及**:`module/alert/*`(controller/service/entity/consume)

### 1. 规则 CRUD 与唯一性

- 创建:枚举合法性(metric/operator/level)+ **五元组查重**(server_id, metric, operator, threshold, level;server_id IS NULL 通用规则独立范围)→ 冲突 40900。
- 数据库侧(V13 迁移):**生成列唯一索引** `uk_alert_rules_active_signature` —— 软删除行生成列置 NULL 不参与唯一,所以删除后允许重建同规则;DuplicateKeyException 兜底。
- 更新:不允许改 metric/operator/serverId(改动相当于删旧建新),只改 threshold/level/enabled,查重排除自身。

### 2. 评估状态机(AlertStateMachine,sealed interface + 穷举 switch)

```
evaluate(state, breached):
  IDLE(无状态行)+ breached        → Trigger(建记录 unread + 建状态行 active + 发 AlertTriggeredEvent)
  ACTIVE + breached               → ContinueBreached(乐观锁刷 last_triggered_at,不建记录)
  ACTIVE + !breached              → Resolve(记录置 resolved + 物理删除状态行)
  其他                            → NoAction
```

- 每规则 try-catch:单条规则失败只 warn,不中断其他规则。
- 查询规则 `ORDER BY server_id DESC, id ASC`:具体服务器规则优先于通用规则。
- `AlertOperator.eval` 用 `BigDecimal.compareTo`(2.0 == 2.00 恒等);metric 缺失(null)不触发。
- 恢复语义 = **删除状态行**(不是置 active=0):恢复后再越界时 state=null 自然重新 Trigger。这是 07-31 修复的真实 Bug(见 05 文档第 6 条),修复 commit `f7dba69`。

### 3. 消息驱动消费(MVP-11,`AlertMessageConsumer`)

```
消费 metrics.reported.v1:
 1. 幂等预检:existsConsumed(consumer='alert-evaluator', eventId) → 命中直接返回
 2. 契约校验:event_id UUID / producer='metrics-service' / occurred_at UTC 偏移 /
    payload 各字段范围与不变量(百分比 0-100、非负、used≤total)
    —— 校验失败抛 AmqpRejectAndDontRequeueException → 零重试直接 DLQ
 3. transactionTemplate.executeWithoutResult:
       evaluate(指标) + INSERT message_consume_records(consumer, event_id)
    —— 业务处理与幂等记录同事务
 4. 方法正常返回 → 容器 AUTO ACK(业务事务成功才 ACK)
异常路径:
 - 可重试(DB 抖动等):ExceptionClassifierRetryPolicy + SimpleRetryPolicy(max 3 次,
   退避 1s→2s→10s),耗尽后 RejectAndDontRequeueRecoverer → DLX → DLQ
 - 不可重试(JSON 解析失败/schema≠1/event_type 不符/字段非法):直接 DLQ
```

> 面试点:为什么弃用 MANUAL ack + afterCommit?真实验收发现 MANUAL ack 在容器回调里容易"滞留"(消息已消费但 ack 未发出,队列堆积)。改为 AUTO + "业务事务在监听方法内提交后才返回"等价于"事务成功才 ACK",语义清晰且队列不堆积。

### 4. 告警推送(AlertPushPublisher)

- `AlertTriggeredEvent` 由 `AlertPushPublisher` AFTER_COMMIT 监听 → 向订阅该 server_id 的浏览器发 `alert.push`。
- 前端 AlertRecordsView:选择具体服务器才建 WS 连接;收到 push 只递增"有 N 条新告警"提示条,点刷新再重拉(避免部分字段不一致)。

## 功能五:Web 终端(浏览器 ↔ Java ↔ Go PTY 全链路)

**涉及**:`module/terminal/*`、`websocket/Terminal*`、`agent-go-SuMon/internal/terminal/*`、`web-vue-SuMon/src/services/terminal-ws.ts`、`views/TerminalView.vue`

### 1. 打开会话的完整时序

```
浏览器 TerminalView(mountXterm + FitAddon)
  → TerminalWebSocket.open():发 terminal.open{server_id, cols, rows}(message_id=UUID)
Java TerminalMonitorRelayService(open 帧):
  ① userService.isApprovedUser(回查最新审核)
  ② serverService.existsActive + agent_status=online(否则 40904)
  ③ openSession 并发控制:
     全局配额锁 + 每 (userId,serverId) 一把 ReentrantLock
     —— 锁释放通过 TransactionSynchronizationManager.registerSynchronization
        (afterCompletion → unlock)绑定到事务结束,避免事务未提交时配额计数不一致
  ④ 幂等:按 (userId, open_message_id) 查重,浏览器重发 open 返回同一会话
  ⑤ 配额:每用户 2 / 每服务器 4 / 全局 16 / 操作中用户 5
  ⑥ 建 TerminalSessionEntity(元数据)+ TerminalRelayRegistry 绑定 monitorSession
  ⑦ 向 payload 注入服务端生成的 server_id/session_id,经 AgentConnectionRegistry
     串行发给 Agent
Go Agent terminal_agent.handle:
  ① 校验 payload(ServerID 必须匹配本 Agent、cols≤300、rows≤100)
  ② manager.Open:会话数上限(默认 4)→ exec.CommandContext(shell=/bin/bash)
     → pty.StartWithSize(Winsize) → 注册
  ③ 回 terminal.opened(带 request message_id 关联 + shellIdentifier=basename)
Java → 浏览器:opened 帧驱动状态机 opening→open
```

### 2. 输入输出转发与限流

- **输入**:浏览器 `terminal.input`(Base64,解码后 ≤16KB)→ Java 控制帧令牌桶(open 6/min burst 2、input 600/min burst 120、resize 60/min burst 20、close 30/min burst 10,超限 42904)→ 转发 Agent → 写 PTY。
- **输出**:Agent 读 PTY(每块 ≤16KB,队列 64 块)→ **字节级令牌桶 256KB/s / burst 512KB** —— 令牌不足**不等待,直接关闭会话**(`output_rate_exceeded`),防止慢消费者拖垮 Agent → Base64 → `terminal.output` 回传。
- **Java 侧输出限流**(TerminalOutputRateLimiter):按**解码后原始字节数**再限一次(双重保护),超限服务端发 `terminal.close` 并收口。
- **浏览器侧背压**:Monitor 会话用 `ConcurrentWebSocketSessionDecorator`(发送时限 5s / 缓冲 256KB / OverflowStrategy.TERMINATE);`SessionLimitExceededException` → MonitorBackpressureException → 统一收口:关终端路由 → 释放限流桶 → 移除订阅 → 关浏览器 socket(1011 SESSION_NOT_RELIABLE)。

### 3. 断连与回收语义

| 场景 | 处理 |
|---|---|
| 浏览器断开 | TerminalRelayLifecycleService:向可达 Agent 发 `terminal.close` + 移除绑定 + 元数据 monitor_disconnected |
| Agent 断开 | 先 `agentRegistry.isCurrent` 过滤被替换的旧连接(旧连接不能关新连接拥有的会话),该服务器所有会话置 error(agent_disconnected) |
| 进程退出 | Go 侧 waitProcess 监听到 shell 退出 → closeSession(process_exited, exitCode)→ 回 `terminal.closed` |
| 空闲/超时 | Agent 侧每秒 watchTimeouts:空闲 20min / 总寿命 8h → 关闭 |
| 强制回收 | closeSession 幂等:closeOnce → kill(-pid, SIGTERM) 杀**进程组** → 5s 未退 SIGKILL → 关 PTY → 删 map → 回调 Closed(无孤儿 shell) |
| Java 定时清理 | TerminalSessionCleanupScheduler 每小时扫空闲 >20min / 总时长 >8h 的会话置 timeout |

### 4. 协议安全(四端共享校验器)

- `TerminalProtocolValidator` 无状态校验四端(浏览器/Android/Java/Agent)所有帧:type/message_id(UUID)/timestamp(UTC) 必填;方向严格分离(浏览器/Android 不能发 opened/output/closed/error;Agent 不能发 open/input/resize/close);**浏览器提供的 server_id/session_id 对已有会话不可信,Java 注入持久化值**。
- 错误码:40003 非法载荷 / 40302 拒绝访问 / 40403 会话不存在 / 40903 状态冲突 / 40904 Agent 离线 / 42903 会话数上限 / 42904 消息限流。

### 限流器实现(可讲细节)

## 功能八:可观测性与运维面
