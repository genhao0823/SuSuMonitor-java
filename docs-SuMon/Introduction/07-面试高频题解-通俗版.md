### Q2 「技术选型为什么这么选」

**一句话核心**：每端选"最合适、最主流"的：后端 Java(Spring)、Agent Go、前端 Vue3、安卓 Kotlin、消息 RabbitMQ。

## 二、可靠性类（本项目最值钱的深度，重点准备）

### Q3 「RabbitMQ 在项目中是怎么用的 / 在哪个环节起作用」

**一句话核心**：RabbitMQ 只承担一个职责——解耦 **指标上报（metrics 模块）→ 告警评估（alert 模块）** 这个异步边界。

**通俗解释**：
- 它**只在 Java 后端内部**两个模块之间起作用；Go Agent 和 Vue 前端都不用（它们走 WebSocket）
- 为什么需要：metrics 快（每秒 60 条，必须立刻回 ACK），alert 慢（要查规则、查历史、跑状态机）。直接调用会互相拖累，加 MQ 让两者互不等待
- 不加 MQ 的风险：告警模块挂/慢/重启时，指标直接丢失，**最严重是告警漏报**

**发送端（生产者）→ 接收端（消费者）**：
```
发送端：module/metrics/outbox/  （OutboxPublisherServiceImpl）
    ↓ 每 200ms 轮询 outbox 表，取"待发信"发到 RabbitMQ
接收端：module/alert/consume/   （AlertMessageConsumer）
    ↑ 从队列 susumonitor.alert.metrics 收消息做告警评估
```

**交换机类型**：Topic 交换机（`susumonitor.events` 业务 + `susumonitor.dlx` 死信）。选 Topic 是因为既能精确匹配当前 `metrics.reported.v1`，又能用通配符将来扩展新事件。

**面试 30 秒话术**：
> 项目里 RabbitMQ 只做一件事：解耦"指标上报"和"告警评估"。因为指标每秒上报、必须快，告警评估要查规则和历史、可以慢，直接调用会互相拖累。发送端是 metrics 模块的 Outbox 发布器，每 200ms 从 outbox 表取消息发到 Topic 交换机 `susumonitor.events`，消费端是 alert 模块的消费者，从队列取消息做评估。前端和 Go Agent 都不走 MQ。

**追问&应对**：
| 追问 | 应对 |
|---|---|
| "为什么不是一对多？" | 项目里是 1 生产者 + 1 消费者；文档明示"单消费者当前，多消费者并发未验证" |
| "交换机为什么用 Topic？" | 能精确匹配当前路由键，也能用 `*`/`#` 通配符扩展新事件类型 |

### Q4 「Outbox 模式是什么？为什么能保证不丢消息」⭐

**一句话核心**：Outbox 模式 = 把"发消息"变成"往数据库表写一行"，和业务落库同一个事务，从根上保证消息不丢。

**通俗解释（托盘比喻）**：
- 业务落库时，**同一个数据库事务**里同时往 `message_outbox` 表（待发托盘）插一行"待发信"
- 后台定时器（200ms）轮询托盘，读到就发给 RabbitMQ，**拿到 Publisher Confirm 回执才标记"已发送"**
- 发失败不丢弃：`attempts+1` + 指数退避（`min(2^n, 300s)`）回写 `next_attempt_at`，Broker 恢复后自动补发

**为什么需要**：MySQL 和 RabbitMQ 是两个系统，无法原子提交。先落库后发消息 → 发失败就丢；先发消息后落库 → 落库失败产生"幽灵消息"。

**关键实现**：
- `OutboxServiceImpl`：同事务写 outbox 表
- `OutboxEnvelopeFactory`：MetricsEntity → JSON 信封（snake_case）
- `OutboxPublisherServiceImpl.publishRow()`：`convertAndSend` + 同步等 Confirm（5s 超时）
- `OutboxMapper.selectPendingForPublish`：`FOR UPDATE SKIP LOCKED`（多实例不抢同一行）

**面试 30 秒话术**：
> 指标落库和发消息是两个系统，没法原子提交。我们的解法是：落库的同一个事务里，把"待发消息"也写进 outbox 表。然后后台 200ms 轮询这张表，读到就发 RabbitMQ，拿到发布确认才标记已发，失败就指数退避重试。只要指标落库成功，消息一定最终送达。真实验收：Broker 停机期间指标照常落库，恢复后 6/6 消息补发无丢失。

**追问&应对**：
| 追问 | 应对 |
|---|---|
| "为什么不用先发消息再落库？" | 那会产生幽灵消息——消息发出去了但数据库里查不到数据，消费方拿到空数据 |
| "outbox 表会无限膨胀吗？" | 有清理任务（30 天保留，默认关闭避免升级误删证据） |
| "轮询为什么不设成事件触发？" | 轮询 + 数据库天然支持"换人接班"——发布器挂了重启还能从托盘继续，不丢状态 |

### Q5 「消息重复消费怎么办？怎么保证幂等」⭐

**一句话核心**：至少一次投递必然带来重复，用**三层幂等**兜底。

**通俗解释（三层防线）**：
| 层 | 幂等键 | 位置 |
|---|---|---|
| ① 入口层 | `message_id`（Agent 每条指标带 UUID） | `metrics_ingestions` 表唯一键 `(server_id, message_id)`，重复插入静默跳过 |
| ② 出口层 | `event_id`（每条消息带 UUID） | `message_consume_records` 表唯一键 `(consumer, event_id)`，消费前先查 `existsConsumed` |
| ③ 业务层 | 状态机"持续越界"不重复建记录 | `AlertStateMachine` ContinueBreached 不重复触发 |

**面试 30 秒话术**：
> 至少一次投递意味着消息可能重复，所以做了三层幂等：入口层，Agent 每条指标带 message_id，数据库唯一键兜底；出口层，每条消息带 event_id，消费方有消费记录表，消费前先查；业务层，告警状态机持续越界不重复建记录。真实验收里 50 对重复 message_id，幂等命中 100%。

### Q6 「消费失败怎么办？重试和死信怎么处理」

**一句话核心**：错误分两类——临时故障有限重试，永久错误零重试直接进 DLQ。

**通俗解释**：
| 失败类型 | 例子 | 处理 |
|---|---|---|
| 可重试（临时） | 数据库抖动、网络瞬断、锁冲突 | 容器级有限重试 3 次 + 指数退避（1s→2s→4s，上限 10s），耗尽进 DLQ |
| 不可重试（永久） | JSON 解析失败、schema 版本不支持、CPU=200%、UUID 非法 | `AmqpRejectAndDontRequeueException` 零重试直接 reject → DLQ |

**为什么坏消息不重试**：格式错的消息重试 100 次还是错的，只会卡住队列。进 DLQ 让运维人工处理。

**DLQ 不自动回投**（防无限循环），用 `api-test/replay-dlq.mjs` 人工重放（`--replay`）或清空（`--purge`），重放靠 `event_id` 幂等防重复。

**配套**：`FailedConsumeRecordRecoverer` 在 reject 前尽力写 failed 留痕（attempts + last_error 截断 500 字符）；DLQ 重放成功后 failed→consumed 翻转。

### Q7 「ACK 怎么配的？为什么用 AUTO 不用 MANUAL」⭐

**一句话核心**：用 AUTO 确认 + 业务事务提交完才返回 = "事务后 ACK"，比 MANUAL 更安全。

**通俗解释**：
```java
@RabbitListener(queues = "susumonitor.alert.metrics")
public void onMessage(Message message) {
    MetricsReportedMessage env = parseEnvelope(message);
    if (consumeRecordMapper.existsConsumed(...)) return;   // 幂等
    transactionTemplate.executeWithoutResult(status -> {   // ★ 业务事务
        evaluationService.evaluate(env.payload().toMetricsLatestVo());
        insertConsumeRecord(env);                          // 幂等记录同事务
    });
    // 事务提交完才走到这 → 方法返回 → Spring 自动 ACK
}
```

- 事务提交完 → 方法返回 → AUTO ACK ✓
- 事务回滚 → 抛异常 → 不 ACK → 触发重试 ✓
- 进程崩在事务提交后但 ACK 前 → 没 ACK → 重投 → 幂等防重复 ✓

**为什么不用 MANUAL**：项目一开始用 MANUAL + afterCommit，真实验收发现**消息滞留 unack 堆积**（spring-amqp 回调行为问题：RejectAndDontRequeueRecoverer 只打日志不 reject）。改用 AUTO + 业务事务后解决。

### Q8 「告警状态机怎么设计的？为什么恢复要删状态行」⭐

**一句话核心**：三态状态机（IDLE→ACTIVE→RESOLVED）+ 持续越界不重复触发 + **恢复必须删状态行而不是置 0**。

**通俗解释**：
- 迁移：IDLE→ACTIVE（触发）、ACTIVE→ACTIVE（ContinueBreached，不重复建记录）、ACTIVE→RESOLVED（恢复）
- **逃逸窗口**：`confirm_count > 1` 时走 CountingStart/CountingProgress，防单次抖动误报
- 乐观锁：`alert_states.version`，冲突只 warn 跳过本轮（状态机可重复评估）

**关键教训（真实 bug，commit f7dba69）**：
> 恢复时如果把状态**置 0**，会掉进状态机的 NoAction 死区，导致"恢复后再越界"永远不触发。正确做法是**删除状态行**——下次评估查到 null 就能重新进入 IDLE 再触发。

### Q9 「生产者的数据在源码里是怎么传递的（数据形态流转）」

**一句话核心**：同一份指标数据，形态沿 6 个阶段变化：Java 对象 → JSON → MySQL → Java 对象 → AMQP 字节 → 队列。

**6 阶段对照**：
| 阶段 | 形态 | 在哪做 | 说明 |
|---|---|---|---|
| ① | Java 对象（MetricsEntity） | JVM 堆 | 驼峰字段，内存表示 |
| ② | JSON 信封字符串 | `OutboxEnvelopeFactory.build()` | 驼峰→snake_case，加 event_id/event_type 等信封字段 |
| ③ | MySQL 一行（payload TEXT） | `OutboxMapper.insert()` | 和 metrics 表同事务写入 |
| ④ | Java 对象（OutboxEntity） | `OutboxMapper.selectPendingForPublish()` | 反查回来，payload 还是字符串 |
| ⑤ | AMQP 字节流 | `RabbitTemplate.convertAndSend()` | String → UTF-8 byte[] → AMQP 帧 |
| ⑥ | RabbitMQ 队列里的字节 | 队列文件 | durable 持久化，等消费者 |

**面试 30 秒话术**：
> 生产者的数据从头到尾只有一份内容——指标数据。形态沿这条链路变化：Java 对象 → JSON 字符串（驼峰转下划线、加信封字段）→ 存进 MySQL outbox 表 payload 字段 → 发布器反查回来 → convertAndSend 序列化成 UTF-8 字节 → 进入 RabbitMQ 队列。关键代码在 OutboxEnvelopeFactory 和 OutboxPublisherServiceImpl。

## 三、安全类

| 问题 | 一句话核心 | 要点 |
|---|---|---|
| JWT 怎么做？ | HS256 签发 + 每请求回查数据库 | 过滤器每个请求查库验证用户仍 approved → 管理员审核/禁用即时生效，不用等 72h 过期；代价是每次一次查询，单实例可接受 |
| 密码怎么存？ | BCrypt 哈希 | 登录时对不存在的用户也执行一次假 BCrypt 比较，消除用户枚举时间侧信道 |
| Agent 怎么鉴权？ | 首帧 authenticate + 哈希比较 | 连接后 10s 内发 `agent.authenticate`，token 存 SHA-256 哈希、`MessageDigest.isEqual` 恒定时间比较；Token 从不在 URL 传输防日志泄露 |
| 浏览器 WS 怎么鉴权？为什么 JWT 不放 URL？ | 一次性 ticket | JWT 进 URL 会被访问日志/历史记录泄露；`POST /api/ws/monitor-ticket` 换 32 字节一次性 ticket（30s TTL，内存 ConcurrentHashMap，`remove()` 原子消费），握手时从 `?ticket=` 消费 |
| SSH 凭据怎么存？ | AES-256-GCM + AAD | 密钥绑定服务器 ID + 凭据类型（AAD），密文被搬到别的服务器行就解密失败；12B IV + 128b tag |
| 防 SSRF 怎么做？ | 出站白名单 | CIDR 白名单 + 端口白名单 + 云元数据地址黑名单 + DNS 结果逐 IP 校验 + 数量上限 |
| 限流怎么做？ | 手写令牌桶 | 没引第三方库，按消息类型分桶：握手 10/min、心跳 12/min、指标 24/min、终端每类独立、输出 256KB/s；超限先发业务错误码帧再延迟 50ms 关闭 |

**追问&应对（JWT 为什么每请求查库，面试常追问）**：
> 审核/角色变更要立即生效，不能等 token 过期；代价是每个请求多一次 DB 查询，单实例下可接受——安全 > 性能。

## 四、架构与并发类

### Q9 「Web 终端为什么不用 SSH 直连」

**一句话核心**：被监控机器多在家庭内网/无公网 IP，主动 SSH 进不去，所以改成 Agent 主动出站 + 远端 PTY。

**通俗解释**：
```
浏览器 → WebSocket → Java 后端（只做路由和元数据）→ WebSocket → Go Agent（执行 PTY）
```
- Agent 主动出站连后端，对无公网 IP 的机器友好
- Java 只做路由与元数据，**终端内容不落库**
- 三重限流：控制帧 4 类令牌桶（open 6/min、input 600/min、resize 60/min、close 30/min）+ 输出 256KB/s + 浏览器背压（5s/256KB → 1011）
- Agent 侧安全边界：最大 4 会话、单块 16KiB、空闲超时 20min、生命周期 8h、SIGTERM→SIGKILL 回收进程组

### Q10 「事务和并发怎么处理的」

| 问题 | 答案要点 |
|---|---|
| 并发注册首管理员怎么保证唯一？ | 三重：`FOR UPDATE` 行锁 + `WHERE admin_initialized=0` 条件更新 + 唯一索引（诚实：空库真实并发没跑过） |
| 指标乱序怎么拒绝？ | `FOR UPDATE` 锁服务器行串行化写入 + `collected_at` 严格递增，违反回 `metrics.nack(stale_collected_at)`，Agent 移入死信不重试 |
| 乐观锁用在哪？ | 告警状态机 version、Agent 心跳防旧连接覆盖新连接、SSH 指纹 CAS 写入、consumed 状态翻转 |
| 多实例部署怎么办？ | 诚实：当前单 JVM，内存态（ticket/注册表/订阅）不支持横向扩容；设计思路已备（事件改 MQ、注册表改 Redis、ticket 改 SETNX） |
| AFTER_COMMIT 是什么？ | `@TransactionalEventListener(phase = AFTER_COMMIT)`：业务事务提交后才推送/发通知，回滚不推——保证"前端看到的，数据库一定有" |

## 五、Go Agent 专题

### Q12 「Agent 采集是怎么实现的」

**一句话核心**：用 gopsutil 库每 5 秒读一次系统快照，打包成和后端宽表一一对应的结构，序列化 JSON 走 WebSocket 上报。

**通俗解释**：
- **为什么用 gopsutil 不解析 /proc**：跨平台——一份代码跑 Linux/Windows/macOS，gopsutil 是采集事实标准
- **采集 6 类指标**：CPU（1s 采样窗口瞬时值）、内存（已用/总量/百分比）、磁盘（Windows 采 C:，Linux 采 /）、网络（累计字节）、温度（可选）、负载（可选）
- **采集循环**：`time.NewTicker(5s)` 驱动，启动先采一次，每 5s 采一次，`ctx.Done()` 优雅退出
- **可选字段降级**：温度/负载读不到返回 nil（JSON null），不影响其他指标
- **细节**：`cpu.Percent(1s, false)` 过去 1 秒采样窗口（瞬时值不准）；数值 round 到 2 位小数；网络是开机累计值

**面试 30 秒话术**：
> Agent 用 gopsutil 库采集，不自己解析 /proc——因为它跨平台，一份代码跑 Linux/Windows。每 5 秒用 Ticker 触发一次采集，一次读 CPU（1 秒采样窗口）、内存、磁盘、网络累计字节，温度和负载是可选的，读不到返回 null 不影响其他。采集结果打包成和后端 MySQL 固定宽表字段一一对应的结构体，序列化 JSON，加 UUID message_id 和 UTC 时间戳，走 WebSocket 上报。

**追问&应对**：
| 追问 | 应对 |
|---|---|
| "CPU 怎么算的？" | `cpu.Percent(1s, false)` 过去 1 秒采样窗口，不是瞬时值（瞬时值波动大） |
| "网络是增量还是累计？" | 累计值（BytesRecv/BytesSent），后端不关心增量 |
| "采集失败怎么办？" | 核心指标失败 → 整次采集失败返回 error；可选指标失败 → 跳过不阻塞 |
| "为什么用指针字段？" | 表示可空（null），和后端宽表的可空列对应 |
| "怎么测的？" | gopsutil 函数包成字段注入假函数，单测不真读系统 |

### Q13 「Agent 指标可靠投递（M1-M4）怎么做的」

**一句话核心**：先持久化后发送、单帧在途、ACK 驱动出队、NACK 进死信、重传带抖动、积压节流。

**通俗解释**：
| 机制 | 说明 |
|---|---|
| 持久化 FIFO | 发送前把完整帧写 JSON 快照文件（write-tmp → fsync → rename 原子写，0600），崩溃/断网不丢 |
| 单帧在途 | 任一时刻只有一帧 inFlight，保证 collected_at 严格递增（对齐后端乱序拒绝语义） |
| ACK 超时重传 | 发送后 15s 定时器，超时把帧留在队首，指数重传 2s→60s 上限 |
| equal jitter | `half + rand[0, half]` 抖动，避免多 Agent 断线后同步重连惊群 |
| NACK 死信 | 服务端回 `metrics.nack`（invalid/stale/server_not_found），队首移入本地死信，绝不重试 |
| 积压节流 | 积压时按 2500ms 最小间隔逐帧重放，避免恢复时触发服务端限流 |
| 投递遥测 | 心跳携带 pending/drop/dead-letter 统计，后端存库供状态展示 |

### Q14 「npm run dev 和 npm run build 有什么区别」

**一句话核心**：dev 是开发模式（本地服务器 + 热更新），build 是生产构建（打包成 dist/ 静态文件）。

**对比**：
| 维度 | npm run dev | npm run build |
|---|---|---|
| 目的 | 开发调试 | 生产部署 |
| 运行方式 | 持续进程 | 一次性命令 |
| 产物 | 无（内存里跑） | dist/ 目录（静态文件） |
| 压缩 | 否（好调试） | 是（体积小加载快） |
| 热更新 | ✅ | ❌ |
| 能否部署 | ❌ | ✅（扔 Nginx 就能用） |

**项目真实命令**：
```json
"dev": "vite",
"build": "vue-tsc --noEmit && vite build"   // 先类型检查再打包
```

**常见坑**：dev 能跑不代表 build 能过（build 会做严格类型检查）；`VITE_` 前缀环境变量 dev/build 可能不同。

### Q15 「Element Plus 按钮在 dev/build 下有没有兼容性问题」

**一句话核心**：按钮组件本身**没有任何差异**——dev 和 build 用同一份 Element Plus 源码，渲染一致。

**真正可能的坑**：
- Element Plus 是**按需自动引入**（unplugin-vue-components + ElementPlusResolver），dev 按需加载、build 打包进产物，但组件本身无差异
- 真正的坑：`auto-imports.d.ts` / `components.d.ts` 是 Vite 启动时自动生成的，**刚 clone 项目直接 build** 时 `vue-tsc` 类型检查找不到类型文件会报错。解决：先 dev 生成一次，或把 .d.ts 提交进 git

### Q16 「登录按钮点击无反应」排查故事（面试宝藏）

**一句话核心**：现象是"点击无反应、network 0 请求"，根因不是按钮组件，而是 `crypto.randomUUID` 在明文 HTTP（非安全上下文）下不可用，axios 拦截器同步抛错。

**完整故事（现象→排查→根因→修复→教训）**：
> **现象**：部署到服务器后，点登录按钮完全没反应——console 无报错、network 0 请求。
>
> **排查**：一开始怀疑按钮组件（当时用 Element Plus 的 el-button），换了原生 button 还是没反应，排除组件。看 network 面板发现 0 请求——说明请求根本没发出，问题在"发出之前"，也就是 axios 拦截器。
>
> **根因**：`crypto.randomUUID()` 是**安全上下文专属 API**，只有 HTTPS 或 localhost 下可用。明文 HTTP 下它是 undefined，拦截器同步抛 TypeError，请求在 dispatch 前被 reject。
>
> **修复**：`newCorrelationId()` 加 typeof 守卫，不可用降级 `Date.now()-random`；WS 的 message_id 因后端要求标准 UUID，用 `crypto.getRandomValues` 生成 UUID v4 降级。后来上 HTTPS 彻底根除。
>
> **教训**：前端"点击没反应"先看 network 面板——0 请求说明问题在发出前（拦截器/事件），有请求无响应才是服务端问题；安全上下文 API 在 HTTP 下不可用，部署前就要意识到。

**⚠️ git 查证结论（重要，别讲错）**：
> 换按钮和 randomUUID 修复是**同一次提交** `830aec1`（2026-07-31），里面同时做了三件事：① el-button → 原生 button（现在代码是原生 button 蹭 el-button class）；② crypto.randomUUID 降级修复（真正根因）；③ 去掉 handleSubmit 里的 formRef.validate() 拦截。
>
> 面试**别只讲"换组件就好了"**（停在表象），要讲"先怀疑组件、换了没用、看 network 发现 0 请求、追到拦截器、找到真正根因是 randomUUID"——这才显排查能力。

**追问&应对**：
| 追问 | 应对 |
|---|---|
| "为什么换组件没用？" | 根因不在组件——@click 正常触发，是 click 之后调用的拦截器抛错 |
| "降级代码怎么写？" | `typeof crypto !== 'undefined' && typeof crypto.randomUUID === 'function' ? crypto.randomUUID() : \`${Date.now()}-${Math.random().toString(16).slice(2)}\`` |
| "降级 ID 有安全风险吗？" | 它只用于 X-Correlation-ID 关联追踪，不是安全凭据；需严格 UUID 格式的 message_id 用 getRandomValues 保证 |
| "为什么 localhost 开发没暴露？" | localhost 属于安全上下文，只有部署到明文 HTTP 才暴露——"本地好好的、上线就炸"的典型 |

## 十一、项目全貌速查（Q1 详细介绍素材）

> 本章是完整自述材料（业务流程 → 功能模块 → 技术架构 → 模块设计详解），与前文 Q&A 章节存在刻意重复：面试开场介绍需要一口气讲完，不适合跳读。建议用法：30 秒版用 Q1 话术；3 分钟版用本章第 1~2 节；被追问细节再切回对应 Q。

### 1. 业务流程总览（回答"项目是干什么的"）

**业务闭环**：注册/审核 → 录入服务器 → 部署 Agent → 指标采集 → 实时展示 → 告警判定 → 多渠道通知 → 处理告警（Web 终端）。

| 环节 | 流程 | 关键点 |
|---|---|---|
| ① 用户认证与审核 | 注册 → pending 待审核 → 管理员 approve/reject | 首注册用户自动成为管理员（行锁）；被拒绝用户登录立即失效（每请求回查 DB） |
| ② 服务器接入 | 管理员录入服务器（SSH 凭据加密）→ 签发 Agent Token → 配置到 Go Agent | Agent 主动出站长连接，无需公网 IP/入站端口 |
| ③ 指标采集（核心） | Agent 每 5s 采集 → `metrics.report` 上报 → 幂等去重 → 宽表入库 → 同事务登记 Outbox | 入库后两条通道：AFTER_COMMIT 实时推浏览器 + Outbox 可靠投递 RabbitMQ |
| ④ 告警判定 | MQ 消费 → 状态机评估（逃逸窗口防抖动）→ Trigger/Continue/Resolve | 触发时：WS 实时推送 + 邮件/钉钉/Webhook 通知（失败指数退避） |
| ⑤ 在线状态 | 30s 心跳 → `heartbeat.ack`；90s 无心跳置离线 | 乐观锁防旧连接误标离线 |
| ⑥ Web 终端 | 浏览器 xterm → WS 中继 → Agent 上 /bin/bash（PTY） | Java 只做路由，终端内容不落库 |

### 2. 功能模块总览（回答"项目有哪些功能"）

**后端 8 大功能模块**（`server-java-SuMon/src/main/java/com/susumonitor/server/`）：

| 模块 | 职责 | 核心能力 |
|---|---|---|
| `module/auth` | 认证授权 | 注册/登录/JWT、审核状态分级放行、首管理员行锁 |
| `module/server` | 资产管理 | 服务器 CRUD（软删除）、SSH 凭据加密、SSH 测试（指纹+SSRF 防护）、Agent Token 生命周期 |
| `module/metrics` | 指标监控（核心） | 上报接收（幂等/乱序拒绝）、宽表存储、Outbox 可靠投递、实时推送 |
| `module/alert` | 告警管理 | 规则 CRUD、状态机评估、MQ 消费（幂等+重试+DLQ）、通知外发（邮件/钉钉/Webhook） |

**各端技术栈**：

|---|---|
| 后端 | Java 21（虚拟线程）+ Spring Boot 3.4.7 + MyBatis-Plus 3.5.12 + MySQL 8.4 + Flyway + JJWT(HS256)+BCrypt + AES-256-GCM + sshj 0.39 + Spring AMQP + springdoc-openapi |

**关键架构机制**：
- **数据架构**：14 张表；幂等两张表（`metrics_ingestions` 入口 / `message_consume_records` 出口）；软删除统一风格（delete_token/生成列规避唯一索引占用）；时间统一 UTC（禁用 NOW()）
- **消息架构**：Outbox（200ms 轮询 + `FOR UPDATE SKIP LOCKED` + Publisher Confirm + 指数退避）+ 消费幂等 + 3 次重试 + DLQ 不自动回投（人工重放）
- **WS 双通道**：`/ws/agent`（Agent 首帧 Token 认证）+ `/ws/monitor`（浏览器 30s 一次性 ticket 认证，Origin 白名单）
- **统一错误码**：`{code, message, data}` 信封，20 个核心码，与 OpenAPI + 前端 `error-code.ts` 三方对齐
- **可观测性**：`X-Request-ID`（服务端 UUID + MDC）+ `X-Correlation-ID`（前端透传，正则白名单）

**核心设计决策（背熟）**：Go Agent 主动出站（家庭内网可监控）｜ 指标宽表（查询可索引）｜ Transactional Outbox（双写一致性）｜ 至少一次 + 双端幂等（工程可行）｜ AES-GCM + AAD 绑定上下文（挪库即解密失败）｜ JWT 每请求回查（审核即时生效）｜ JWT 不进 WS URL（防日志泄露）｜ Java 不落终端内容（敏感通道最小化）｜ 乐观锁 CAS 贯穿（无分布式锁防并发错乱）｜ 模块化单体 + 数据所有权契约（为拆分留边界）。

**工程化门禁**：4 道测试防线（Vitest 124 → 静态扫描 11 条 → api:e2e → ui:e2e）；后端 442 测试全绿；OpenAPI 双向漂移检查 husky 强制。

### 4. 各模块设计与实现详解（回答"XX 模块怎么实现的"）

#### 4.1 认证模块（auth + security）

| 设计点 | 实现方案 |
|---|---|
| JWT | HS256（启动校验密钥 ≥32 字节），72h 过期 + 30s 时钟偏移；claims 含 iss/aud/sub/username/jti，解析强制校验 issuer/audience/算法头 |
| 每请求回查 DB | `JwtAuthenticationFilter`（OncePerRequestFilter，挂在 UsernamePasswordAuthenticationFilter 之前）每请求 `selectAuthenticationUserById`，要求 approved + token 内 username 与 DB 一致 → 被驳回/改名/降级立即失效 |
| 防用户名枚举 | 构造时预计算 dummy hash，登录时对不存在的用户也执行 `matches()`，耗时一致 |
| 首管理员 | 事务内 `SELECT ... FOR UPDATE` 锁 `auth_bootstrap_state` id=1 行 + 条件更新 `WHERE admin_initialized=0`，并发注册串行化，最多一个管理员 |
| 授权映射 | DB 角色拼 `ROLE_ADMIN/ROLE_USER`，SecurityConfig 路径规则区分权限 |

#### 4.2 服务器管理模块（server）

| 设计点 | 实现方案 |
|---|---|
| 软删除 | `deleted=1` + UUID delete_token；改 SSH 目标时 `CASE WHEN` 自动作废主机密钥 |
| SSH 凭据加密 | `CredentialCipher`：AES/GCM/NoPadding，12B 随机 IV + 128b tag，**AAD=`susumonitor:server:%d:credential:%s` 绑定 serverId+类型**；存储 `v1:Base64(IV‖密文)`；密钥必须 32 字节否则启动失败 |
| SSH 测试 | sshj + 虚拟线程 + Semaphore(8) 限并发 + 30s 整体超时；指纹自算 SHA256（OpenSSH 格式）；凭据只在指纹确认后才解密，解密前重查 DB 快照比对 9 字段 |
| 指纹确认 CAS | 条件更新 `WHERE ... fingerprint <=> #{previousFingerprint}`，0 行重查判断 404/409，防并发轮换 |
| SSRF 防护 | `SshOutboundPolicy`：端口白名单 + CIDR 白名单 + 云元数据黑名单（169.254.169.254 等）+ DNS 逐 IP 校验 + 数量上限；连接直接用已校验 IP 不二次解析 |
| Agent Token | 32B SecureRandom → URL-safe Base64，DB 只存 SHA-256 哈希（`MessageDigest.isEqual` 常量时间比较）；register→rotate→revoke 全条件更新，撤销后旧 Token 无法上线 |

#### 4.3 指标模块（metrics + outbox）

`MetricsServiceImpl.report` 单事务完成 6 步：① `SELECT FOR UPDATE` 锁 servers 行（防指标写入期间被软删）② 插 `metrics_ingestions`，`DuplicateKeyException` 即重复静默跳过 ③ 比对 `MAX(collected_at)` 乱序拒绝（NACK）④ 写 12 列宽表 ⑤ 同事务 `outboxService.enqueue`（OutboxServiceImpl 自身不开事务，靠调用方保证"已入库必有事件"）⑥ 发布领域事件，监听器 AFTER_COMMIT 才推送。

**Outbox 关键实现**：状态仅 `PENDING→PUBLISHED`（刻意不设 failed，失败靠 attempts 退避留痕）；取数 `FOR UPDATE SKIP LOCKED`（多实例安全）；`CorrelationData` 同步等 Confirm（5s 超时）ack 才 `markPublished`（带 `WHERE status='pending'` 防重）；失败指数退避 `min(2^n, 300s)`；200ms 轮询。

#### 4.4 告警模块（alert）

| 设计点 | 实现方案 |
|---|---|
| 规则模型 | 五指标 × 四运算符（BigDecimal.compareTo，null 不触发）× warning/critical × confirm_count 逃逸窗口；五元组签名查重（应用层 EXISTS + DB 唯一索引双保障） |
| 状态机 | `AlertStateMachine` 纯逻辑无 IO，状态用 **行存在性 + active 布尔 + breach_count + version** 表达（无字符串状态列）：无行+越界→Trigger/CountingStart；计数中越界→CountingProgress→达阈值升级 Trigger；active+越界→ContinueBreached（防风暴）；active+恢复→Resolve（记录置 resolved + **删行**，下次可再触发）；计数中恢复→CountingReset（中断连续越界）；全部写操作 `WHERE version=#{version}` 乐观锁 |
| MQ 消费 | AUTO ACK：业务事务（评估+幂等表插入）提交成功才返回 → 事务后 ACK；`ExceptionClassifierRetryPolicy` 区分不可重试数据错误（直接 reject→DLQ）与可重试（3 次指数退避 1s×2 上限 10s）；耗尽 `FailedConsumeRecordRecoverer` 写 failed 留痕再 reject |
| 通知 | AFTER_COMMIT → `@Async` 异步发送；每渠道一行 `alert_notifications`（email 需总开关+JavaMailSender / 钉钉 POST text 消息 / webhook POST 记录 JSON）；**至少一个渠道送达才回写记录**；失败 `min(2^n, 60s)` 退避最多 5 次；30s 重试调度器扫到期 pending（单轮 ≤50） |

#### 4.5 终端模块（terminal）

- **中继路由**：`TerminalRelayRegistry` 维护 `sessionId → binding(monitorSession)`，转发目标始终是创建会话的那个浏览器连接；Agent→浏览器方向校验 server_id 必须等于 Agent 自身（防串台）
- **配额**：全局 ReentrantLock + 每 (userId:serverId) 锁（事务完成经 `TransactionSynchronization.afterCompletion` 释放）；用户 2 / 服务器 4 / 同服务器操作用户 5 / 全局 16
- **限流**：输出 256KB/s 令牌桶（先 Base64 解码算真实字节，突发 512KB）；控制帧按 `sessionId:messageType` 分桶（open 6/min、input 600/min、resize 60/min、close 30/min）
- **背压**：`ConcurrentWebSocketSessionDecorator`（5s 发送超时 + 256KB 缓冲 + TERMINATE）→ `SessionLimitExceededException` → `terminateForBackpressure`（CAS 保证只收口一次）
- **生命周期**：空闲 20min / 总寿命 8h，每小时清理

#### 4.6 WebSocket 层

| 通道 | 实现方案 |
|---|---|
| `/ws/agent` | 握手前按 IP 令牌桶限流（10/min，LRU 4096）；不配 Origin 白名单（Go 不带 Origin，安全性靠首帧 Token + 10s 超时关闭）；`replace()` 踢旧连接；`markAuthenticating()` 防扫描误杀慢认证 |
| `/ws/monitor` | `POST /api/ws/monitor-ticket` 签发 32B 随机 ticket（30s TTL，ConcurrentHashMap，`remove()` 原子消费即一次性）→ 握手消费；Origin 白名单防 CSWSH；64KB 上限，坏 JSON 回 error 帧不断连 |
| 订阅模型 | `MonitorSubscriptionRegistry` 双索引（sessionId→session、serverId→session 集合），订阅幂等 |
| 心跳/离线 | 30s 心跳；30s 扫描 90s 超时置离线；`markOfflineOnDisconnect` 带 `WHERE last_heartbeat_at=本会话心跳时间` 乐观锁，新连接已重连则不误标 |

#### 4.7 调度层（8 个 @Scheduled）

| 任务 | 周期 | 动作 |
|---|---|---|
| Outbox 发布 | 200ms | SKIP LOCKED 取数 + Confirm 发布（开关 rabbitmq.enabled） |
| 指标清理 | cron 每日 3 点 | 批删 1000/批 ≤100 批，防重入 |
| Outbox 清理 | cron 3:30（默认关） | 清 30 天前已 published |
| 终端清理 | cron 每小时 | 空闲 20min / 总寿命 8h |
| 心跳离线扫描 | 30s | 90s 阈值 + 乐观锁 |
| 未认证连接关闭 | 5s | 10s 超时 |
| ticket 清理 | 60s | 防内存无界 |
| 通知重试 | 30s | 单轮 ≤50 条 |

#### 4.8 横切层（common/config）

- **common**：`ApiResponse{code,message,data}` + `ErrorCode`（绑定 HttpStatus）+ `BusinessException` + `GlobalExceptionHandler`（参数校验统一映射，日志只记字段名不记值）+ `RequestIdFilter`（最高优先级先于 Security，401/403 也带 `X-Request-ID` + MDC）
- **config**：`RabbitMqTopologyConfig`（@ConditionalOnProperty，启动幂等声明 topic+DLX+DLQ 四件套）；`AppProperties`（@Validated 嵌套校验，非法配置启动即失败）；`ClockConfig` 统一 `Clock.systemUTC()` 注入（测试可控）

### 5. 三分钟完整介绍话术（串起全貌）

> 我做的是一个 Linux 服务器监控平台，四端组成：Go Agent 装在每台被监控机器上采集 CPU/内存/磁盘等指标；Java 后端是 Spring Boot 模块化单体，负责认证、存储、告警和终端中继；Vue3 Web 控制台和 Kotlin Android App 是展示端。核心链路是 Agent 每 5 秒通过 WebSocket 上报指标，后端同事务完成幂等去重、宽表落库和 Outbox 事件登记，事务提交后实时推给浏览器、异步经 RabbitMQ 投给告警模块做状态机评估，越界就触发告警并多渠道通知，需要处置时还能直接开 Web 终端。可靠性上我重点做了四件事：Outbox 保证指标和消息双写一致、三层幂等兜住至少一次投递、告警状态机防重复触发和抖动误报、SSH 凭据 AES-GCM 加密加 SSRF 防护保证安全。整个项目有 442 个后端测试和 13 个真实验收脚本，核心链路做过停机补发 6/6 无丢失、告警延迟 -71% 的性能验证。
