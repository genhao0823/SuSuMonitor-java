## 二、项目类高频问题(⭐ = 必考)

### ⭐ Q1. 介绍一下你这个项目(架构 + 核心链路)
按 01 文档"业务闭环总览"讲:注册→审核→录服务器→发 Token→部署 Agent→指标上报→实时展示→告警→终端处置。每讲一步带一句实现要点(幂等、状态机、限流等),展示你懂实现而不只是功能。

### ⭐ Q2. 为什么用 Go 写 Agent 而不是 Java?
- 单文件静态二进制(CGO_ENABLED=0 交叉编译),部署零依赖,一条命令装 systemd 服务;
- gopsutil 是系统指标采集的事实标准库;
- 并发模型(goroutine + channel)适合"采集循环 + 心跳循环 + 读循环 + 重连循环"这种多循环协作;
- 与 Java 后端职责分离:Agent 只做采集与转发,保持极薄。

### ⭐ Q3. Outbox 模式是什么?为什么需要它?
- 问题:指标落库和发消息是两个系统(MySQL 和 RabbitMQ),无法原子提交 → 要么"数据到了消息没发"(告警漏报),要么"消息发了数据没到"(假告警)。
- 方案:指标行与 `message_outbox` 事件行**同一个数据库事务**写入;后台发布器轮询(200ms)取 pending 行发 RabbitMQ,Publisher Confirm 确认后才标 published,失败指数退避重试。
- 效果:事务提交成功 ⟹ 事件必达(至少一次);Broker 宕机不影响指标落库,恢复自动补发;还天然为未来微服务拆分准备了服务边界。

### ⭐ Q4. 怎么保证消息不重复消费(幂等)?
三层:
1. **入口幂等**:Agent 上报的每条指标带 UUID message_id,`metrics_ingestions(server_id, message_id)` 唯一键,重复投递静默丢弃;
2. **出口幂等**:RabbitMQ 事件带 UUID event_id,消费者先查 `message_consume_records(consumer, event_id)` 唯一键,命中直接返回,评估与幂等记录同事务;
3. **业务层幂等**:告警状态机 Continue 分支不重复建记录。
配合"至少一次投递"语义,重复不可怕。

### ⭐ Q5. 告警状态机怎么设计的?为什么恢复要删状态行?
三态:无状态+越界→Trigger;active+越界→Continue(只刷新时间,防告警风暴);active+恢复→Resolve(记录置已解决+删状态行)。**删行而不是置 0**,否则状态机落到 NoAction 死区,恢复后再次越界永远不触发 —— 这是真实踩过的坑(05 文档 B3),修复后补了跨状态回归用例。

### ⭐ Q6. 浏览器怎么通过 WebSocket 鉴权的?为什么不用 JWT 放 URL?
- JWT 放 URL 会被日志/历史记录泄露;Agent Token 放首帧消息同样为防泄露。
- 方案:`POST /api/ws/monitor-ticket` 用 JWT 换一次性 ticket(32 字节随机数,30s TTL,内存存储),WS 握手 query 带 ticket,后端 `remove()` 原子消费,过期/重复用都 401。

### ⭐ Q7. 心跳和离线判定怎么保证"新连接不覆盖旧连接"?
所有状态更新都带乐观锁:`WHERE last_heartbeat_at = 期望值` 条件更新 —— 只有 DB 里心跳还是断开时的值才置离线;新连接认证成功后 `registry.replace()` 替换旧连接,旧连接断开回调因乐观锁失败不会误把新连接置离线。

### Q8. 指标乱序怎么处理?为什么用行锁?
同一服务器并发上报时,"幂等判定 + 乱序判定 + 写入"需要串行,否则两条并发消息可能交错。`SELECT ... FOR UPDATE` 锁服务器行,把判定与写入放在同一事务内串行;`collected_at` 必须严格递增,等于或小于最新的被永久拒绝——服务端返回 correlated `metrics.nack`(reason=`stale_collected_at`,code=40002),Agent 将队首移入本地死信且不重试。

### Q9. Web 终端为什么这么设计?为什么 Java 不直接开 SSH?
- Agent 模式对家庭内网/无公网 IP 的机器友好(出站连接);
- Java 只做路由与元数据,PTY 在 Agent 上,内容不落库(安全);
- 三重限流:控制帧令牌桶 + 输出字节限流(256KB/s,超限关会话)+ 浏览器背压(5s/256KB → 1011 关闭),防止慢消费者拖垮链路。

### Q10. 慢消费者背压怎么实现的?
浏览器会话用 `ConcurrentWebSocketSessionDecorator`(发送时限 5s / 缓冲 256KB / OverflowStrategy.TERMINATE),发送超限抛 `MonitorBackpressureException` → 统一收口服务:关终端路由 → 释放限流桶 → 移除订阅 → 关闭浏览器 socket(1011)。注意:此路径在真实慢网尚未验收(单机 loopback 触发不了),诚实说明。

### Q11. 为什么 JWT 每请求回查数据库?
审核拒绝/角色变更立即生效,不等 token 过期(最长 72h)。代价是每次请求一次查询,单实例场景可接受。这是"安全 > 性能"的取舍。

### Q12. AES-GCM 加密 SSH 凭据为什么用 AAD?
AAD(Additional Authenticated Data)把密文与"服务器 ID + 凭据类型"绑定:换库、换行、跨类型使用都会解密失败,防止密文被移动/复用。12 字节随机 IV + 128 位 tag 是 GCM 的安全基线。

### Q13. 限流怎么做的?没用第三方库?
手写令牌桶:按 elapsed 补令牌(`tokens = min(capacity, tokens + elapsed*rate)`),单调时钟,每会话独立桶。场景:握手按 IP 10/min、心跳 12/min、指标 24/min、终端控制帧 4 类分桶、输出 256KB/s。超限先发业务错误码帧,延迟 50ms 再关连接(客户端能收到可恢复码)。

### Q14. RabbitMQ 消费侧 ACK 怎么配的?为什么?
AUTO 确认 + 监听方法内 `transactionTemplate` 提交业务事务后才返回 ⟹ 容器只在事务成功后 ACK。曾用 MANUAL + afterCommit,真实验收发现 ack 滞留导致队列堆积,弃用。可重试异常 3 次指数退避(1s→2s→10s)后 reject 进 DLX;不可重试数据错误(JSON 解析失败/schema 版本不符/字段校验失败)零重试直接 DLQ。

### Q15. 首管理员并发注册怎么保证只有一个?
三重:① `SELECT ... FOR UPDATE` 行锁串行化;② 条件更新 `WHERE admin_initialized=0`(0 行受影响即冲突回滚);③ 唯一索引兜底。诚实说明:空库并发未在真实环境跑过,但实现按并发安全设计。

### Q16. 测试体系怎么搭的?为什么这么重视真实验收?
四道防线:Vitest 单元 → audit:catchup 静态扫描 → api:e2e 真实 HTTP → ui:e2e 浏览器。后端 JUnit5 + H2 执行真实 XML + 隔离 MySQL 验证库 IT + 23 个 mjs 验收脚本。原因是吃过亏:单测全绿但 MyBatis 参数绑定错误导致生产 500,H2 与真实 MySQL 行为还有差异 —— 所以核心链路必须真实验收。

### Q17. 项目里你做得最有价值的事?
(二选一)
- 可靠性架构:Outbox + 双端幂等 + 存活/就绪分离,让"消息链路"这个最容易出事的部分有了可验证的保证(Broker 停机三阶段验收 6/6 无丢失);
- 工程纪律:142 篇 dev-log、9 篇 Bug 四段式文档、OpenAPI husky 强制校验、每个里程碑真实验收 —— 让一个人也能高质量推进全栈项目。

### Q18. 如果让你继续做,下一步做什么?

## 三、八股抽查(本项目真实用到的)

| 八股题 | 项目对应 |
|---|---|
| JWT 结构/过期/刷新 | HS256、iss/aud/sub/jti、72h、无刷新机制(诚实说) |
| BCrypt 为什么比 MD5 安全 | 加盐 + 自适应成本;登录用 dummy hash 防时序枚举 |
| Spring Security 过滤器链 | JwtAuthenticationFilter 位置、STATELESS、FilterRegistrationBean 防重复注册 |
| @Transactional 传播行为 | REQUIRES_NEW(告警评估)、AFTER_COMMIT 事件、锁与事务绑定 |
| 乐观锁 vs 悲观锁 | 心跳/指纹/状态机/outbox 用条件更新;服务器行锁用 FOR UPDATE |
| WebSocket vs SSE vs 轮询 | 双向、低延迟(终端需要双向),SSE 只有服务端推 |
| 消息队列为什么至少一次 | 工程现实:Confirm 超时/消费者崩溃都可能导致重复,靠幂等吸收 |
| 虚拟线程 | SSH 握手用虚拟线程 + Semaphore(8)+ 整体超时 |
| Flyway 为什么不能改已执行脚本 | checksum 校验;修复必须新增 V 版本 |
| 软删除怎么处理唯一约束 | delete_token / 生成列 NULL 不参与唯一 |
| SQL 注入防护 | 排序白名单 + `<choose>` 固定分支、MyBatis #{}(预编译) |
| CSRF/CSWSH | 全禁用 CSRF(无状态 JWT);WS Origin 白名单 |
| SSRF | 出站 CIDR/端口白名单、DNS 后逐 IP 校验、云元数据黑名单 |

## 四、亮点话术(每个亮点的"一句话 + 支撑数字")

1. **可靠性**:Outbox 同事务写入,Broker 停机不丢事件 —— 停机 3 次上报 6/6 补消费,恢复自动补发无需重启。
2. **性能**:告警推送延迟优化 -71%(p50 835→242ms,轮询 1000→200ms);10 Agent 并发 19.67/s 线性放大。

5. **工程化**:142 篇 dev-log、9 篇 Bug 四段式、MVP 0→11 全部收口、腾讯云真实部署(HTTPS/WSS，历史验收)、运维手册 5 本。
6. **排查能力**:运营商劫持四组对照实验证据链;时区偏差 8 小时定位(UTC_TIMESTAMP 修复);MANUAL ack 滞留真实验收发现。
