# 开发日志: alert.triggered.v1 消费者接入（消息驱动外部通知）

**日期**: 2026-08-12
**操作人**: ZCode
**阶段**: alert.triggered.v1 消费侧（告警事件发布后下一阶段，M1-M7）

## 背景

上一阶段（`20260812-告警事件RabbitMQ发布.md`）已落地 `alert.triggered.v1` 发布侧：
评估事务内经 Outbox 按行 routing_key（V25）发布到 `susumonitor.alert.triggered` 队列。
本阶段接入消费者 `alert-notifier`，并将外部通知（邮件/钉钉/Webhook）的触发源从
「本地 AFTER_COMMIT 事件直呼」切换为「Broker 消息驱动」——同一 record 只触发一次通知，
Broker 中断恢复后 outbox 补发也能重新触发通知。

## 设计决策（留痕）

- **消息驱动外部通知（用户确认方案）**：通知排程（插 pending 行）在消费事务内与幂等记录
  同事务提交；发送 `@Async` 异步执行，不阻塞消费线程。删除原 `AlertNotificationPublisher`
  （AFTER_COMMIT 直呼 notify）避免双发；WS 推送 `AlertPushPublisher` 保留本地事件（低延迟）。
- **消费事务内查库补全**：`selectActiveRuleById` + `selectRecordById`（与
  `NotificationRetryScheduler` 先例一致）——规则禁用/软删除/无渠道/记录缺失时跳过排程，
  仅落幂等记录（重试无意义）。
- **recoverer 单 bean 双消费**：`FailedConsumeRecordRecoverer` 从消息
  `MessageProperties.consumerQueue` 映射 consumer 名与信封类型
  （`alert.metrics→alert-evaluator` / `alert.triggered→alert-notifier`，缺省回退
  alert-evaluator），两个监听器共用容器工厂与 recoverer，无需新配置键。
- **幂等与 DLQ 分类复用 MVP-11 全套**：V15 唯一键（consumer=`alert-notifier`）、
  AUTO 确认（业务事务提交后 ACK）、不可重试数据错误零重试进 DLQ。

## 改动内容

### M2 消息模型（`module/alert/consume/`）

- `AlertTriggeredMessage` record：信封 5 字段 + Payload 9 字段（snake_case @JsonProperty，
  与 `AlertTriggeredEnvelopeFactory` payload 一一对应；occurred_at/triggered_at 以 String 承载）。
- `AlertTriggeredMessageValidator`：eventId UUID、`producer=="alert-service"`、
  occurredAt/triggeredAt UTC 偏移校验、三 ID > 0、metric ∈ 冻结指标集、数值非空。
- `AlertTriggeredEnvelopeFactory.PRODUCER` 由包私有提升为 public（消费侧同源复用）。

### M3 通知排程拆分（`module/alert/notification/`）

- `AlertNotificationService` 新增：
  - `List<AlertNotificationEntity> scheduleNotifications(rule, record)`：同步、调用方事务内
    为每个配置渠道插 pending 行，返回排程结果。
  - `void sendScheduled(recordId, notifications, rule, record)`：@Async、逐渠道
    `attemptChannel(..., 1)` + 至少一渠道送达回写 `updateNotifiedInfo`。
- 现有 `notify(rule, record)` 保留为兼容组合入口（内部自调用 schedule + send，无代理串行）。

### M4 消费者（`module/alert/consume/`）

- `AlertTriggeredConsumer`（CONSUMER_NAME=`alert-notifier`，QUEUE=`susumonitor.alert.triggered`）：
  - `onMessage`：parseEnvelope（schemaVersion/eventType 对照工厂常量 + validator）→
    `existsConsumed` 幂等命中 return → 事务内 { 规则/记录校验 → `scheduleNotifications` →
    `upsertConsumed` } → 提交后 `@Async sendScheduled`。
  - `DispatchResult` record 携带排程结果供提交后异步发送。
- `FailedConsumeRecordRecoverer`：`recordFailure`/`extractEventId` 的 consumer 名与
  反序列化类型改为按 `consumerQueue` 映射；缺省回退 alert-evaluator/metrics 类型。

### M5 触发源切换

- 删除 `AlertNotificationPublisher.java`（AFTER_COMMIT 直呼 notify）。
- `AlertPushPublisher`（WS 推送）、`NotificationRetryScheduler`（失败重试）不动。

### M6 测试（Maven 全量 506 tests 全绿，基线 486 + 新增 20）

- 新建 `AlertTriggeredConsumerTests`（9 例：幂等/首次排程+发送/规则禁用/无渠道/记录缺失/
  非法 JSON/schema 版本/字段契约/业务异常传播）、`AlertTriggeredMessageTests`（契约反序列化）、
  `AlertTriggeredMessageValidatorTests`（8 例字段校验）。
- 更新 `FailedConsumeRecordRecovererTests`（+3 例：alert 队列 consumer 映射、alert 信封
  event_id 解析、缺省回退）、`AlertNotificationServiceTests`（+3 例：schedule 只排程、
  sendScheduled 发送回写、全失败不回写）。
- 删除 `AlertNotificationPublisherTests`（publisher 已删，等价值由消费者测试覆盖）。
