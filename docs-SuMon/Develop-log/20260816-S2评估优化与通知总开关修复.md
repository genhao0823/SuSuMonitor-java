## 一、模块 A：S2 告警评估性能优化（消除 N 次 SQL 往返）

### 现状
`AlertEvaluationServiceImpl.evaluate()` 对每条规则执行一次 `stateMapper.selectByRuleAndServer(ruleId, serverId)`——100 条规则 = 100 次 SQL 往返，基线 S2 p50 68.62ms / p95 88.81ms，其中 +45ms 全来自查询放大。

### 改动（代码细节与参数传递）
1. **`AlertStateMapper`**：删除 `selectByRuleAndServer`（全仓 grep 确认唯一生产调用点即评估器，不留死代码），新增
   `List<AlertStateEntity> selectByServerId(@Param("serverId") Long serverId)`；
   XML：`SELECT <include refid="StateColumns"/> FROM alert_states WHERE server_id = #{serverId}`（走 V10 已有 `idx_alert_states_server`，**零迁移**）。
2. **`AlertEvaluationServiceImpl.evaluate(metrics)`**：rules 为空仍提前返回；随后**一次** `selectByServerId(metrics.getServerId())`，
   `Collectors.toMap(AlertStateEntity::getRuleId, Function.identity(), (first, ignored) -> first)` 建 `Map<Long, AlertStateEntity> statesByRule`（uk_alert_states_rule_server 唯一键保证无重复，merge 函数纯防御）；
   循环内改为 `evaluateRule(rule, metrics, statesByRule.get(rule.getId()))`。
3. **`evaluateRule(rule, metrics, state)`**：签名新增 state 形参（查询移出循环）；`stateMachine.evaluate(rule, metrics, state)` 与全部 `handle*` 方法不变。全局规则（`server_id IS NULL`）状态行按上报 server 落库，同样被覆盖。

### 测试
- `AlertEvaluationServiceTests`：13 处 stub 从 `selectByRuleAndServer` 重写为 `selectByServerId(1L)` 批量返回（`List.of(state)` / `List.of()` / `thenThrow`）；`noRulesShouldDoNothing` 改 `never().selectByServerId(anyLong())`；`evaluationFailureShouldNotAffectOtherRules` 改为写入失败隔离语义（insertRecord 抛异常→rule2 仍评估）；新增 `stateQueryFailureShouldPropagate`（批量读失败向上传播，由消费者容器重试整条消息）。
- `AlertRecordStateMapperMybatisTests`：新增 `selectByServerIdShouldReturnOnlyThatServersStates`（H2 真实 SQL：2 行 server1 + 1 行 server2 → 返回过滤与字段映射断言）；删除后断言改用 `selectByServerId(1L)` 判空。
- **期间修复**：3 个逃逸窗口测试的 `counting` fixture 原本不设 `ruleId`，旧实现直接 stub 单行查询不经过 Map 所以无感；批量化后 Map 按 `getRuleId()` 建键查不到 → 补 `counting.setRuleId(1L)`。

### 验收（真实环境，2026-08-16）

### 语义变化（诚实声明）
- 批量读失败会向上传播，由 `AlertMessageConsumer` 容器重试整条消息（旧行为：单规则读失败只记 warn、继续其余规则）；逐规则评估/写入失败的 try/catch 隔离保留。
- 该变化在 `stateQueryFailureShouldPropagate` 测试中显式断言。

## 二、模块 B：通知总开关语义修复（notificationEnabled 全渠道门控）

### 现状
`AppProperties.Alert.notificationEnabled` 注释"关闭时不发送任何渠道"，实际 `configuredChannels()` 只对 email 检查开关——钉钉/Webhook 无条件直发（开关关闭时仍插 pending 行并发送）。

### 改动
1. **`AlertNotificationServiceImpl.configuredChannels()`**：方法首行 `if (!appProperties.getAlert().isNotificationEnabled()) { return channels; }`；email 条件去掉开关判断（保留 `mailSender.isPresent() && hasText(notifyEmail)`）；方法注释改为"总开关关闭时不发送任何渠道；邮件另需 SMTP 配置"。
2. **`AppProperties.Alert.notificationEnabled`** 注释同步为"关闭时不为任何渠道排程发送"。
3. 类 javadoc 同步（"均受总开关约束"）。
4. 消费者（AlertTriggeredConsumer/AlertResolvedConsumer）**不改**：开关关闭时 `scheduleNotifications` 返回空列表、`sendScheduled` 不触发（无害路径）。

### 测试
`AlertNotificationServiceTests` 新增 3 例：`shouldNotSendDingtalkWhenDisabledGlobally`、`shouldNotSendWebhookWhenDisabledGlobally`（开关关闭时零 post、零 insert、零回写）、`shouldScheduleNoChannelsWhenDisabled`（三渠道配置但开关关闭 → 空列表）；既有 `shouldNotSendEmailWhenDisabledGlobally` 保持绿色（回归证据）。全量单测 569/569。

### 诚实边界
- 开关关闭**前**已排程的 pending 行仍按退避重试完成或置 failed（关闭语义约束"新排程"，不追溯历史行）；`retry()` 未改。
- 邮件 bean 仍由 spring-boot-starter-mail 自动装配（SMTP host 未配置时以 `Optional.empty` 跳过），"关闭时邮件 bean 不初始化"是 08-05 计划原文，从未如此实现——已在 08-05 计划文档追加带日期注释澄清。

## 三、期间发现与修复（留痕）
