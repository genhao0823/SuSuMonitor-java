## 关键设计要点

- **行级并发保护**:用单值 `busyId` + `busyAction` 控制当前正在处理的行,
  其他行的按钮 `:disabled` 锁定,防止并发审批同用户。
- **二次确认策略**:
  - 通过 = 直接调 API(高频操作,不二次确认)
  - 拒绝 = el-popconfirm 二次确认(低频高代价,避免误点)
- **操作后立即 reload**:approve/reject 成功后调 `fetchPending()` 重拉,
  不在本地 splice(避免后端状态与本地状态不一致)。
- **错误处理**:`explainError` 函数把 `ApiBusinessError.code` 映射为用户可读 toast。
  常规 UI 流程不会触发 40900(详见下文"已知限制")。

## 浏览器手测路径(已实测)

1. 登录 admin → 左侧栏点击"用户审核" → 进入 `/admin/users`
2. 页面加载 5 条 pending 用户(此前探测已知)
3. 点某行"通过" → 该行按钮 loading → toast "已通过 xxx" → 该行从列表消失
4. 点另一行"拒绝" → 弹 el-popconfirm 二次确认 → toast "已拒绝 xxx" → 该行消失
5. 操作某行时,其他行的"通过/拒绝"按钮均 disabled(行级并发保护)
6. 右上角"刷新"按钮 → 重新拉列表
7. 退出登录后访问 `/admin/users` → 跳 `/login?redirect=/admin/users`(路由守卫)
8. 以 user 身份登录 → 访问 `/admin/users` → 跳 `/forbidden`(admin 守卫)
9. admin 登录 → Dashboard → "管理员快速入口"卡 → "前往审核"按钮 → 跳到本页

## 重要: 40900 错误码的实际触发场景

`explainError` 中映射的 `40900 RESOURCE_CONFLICT → "该用户已被审核,请刷新列表查看最新状态"`,
**只在以下并发竞态场景触发**,**常规 UI 流程不会重现**:

| 场景 | 是否能复现 |
|---|---|
| 用户在 A 标签点"通过",网络往返中,后端被另一端 admin 审核 | ✅(竞态) |
| 后端人工 SQL 直接改了 user.reviewStatus | ✅ |
| **常规 UI 流程**(approve 后立即 reload → 该行消失 → 用户找不到行) | ❌ |

之前的浏览器手测路径里我曾错误地写"对已审核用户再点通过 → toast 40900",
**这条路径在 UI 上无法触发**(按钮物理消失),撤回。
**验证 40900 真实路径**需用 curl 直接对后端发请求,不依赖 UI 操作。

## 风险与对策

| 风险 | 处理 |
|---|---|
| 并发点击同一行 | `busyId` 单值互斥 + el-button loading |
| 后端状态变更导致 reload 前 UI 状态过期 | approve 后立即 reload,后端是真实状态源 |
| 误点"拒绝" | el-popconfirm 二次确认 |
| 单行 `busyId` 限制不同行并发 | 当前实现:其他行 disabled,只允许同时操作单行 |
| TypeScript 模板 row 默认 `DefaultRow` | 4 处显式 `as CurrentUser` 断言 |
