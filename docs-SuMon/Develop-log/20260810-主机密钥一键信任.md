# 开发日志: 主机密钥一键信任（observe + 复用登记，详情页弹窗确认）

**日期**: 2026-08-10
**操作人**: ZCode

## 背景

原"主机指纹确认"流程要求管理员带外执行 `ssh-keyscan` 获取指纹后手动输入（详情页弹窗），步骤繁琐。本轮新增**一键信任**：后端只读握手读取目标主机实际公钥 → 详情页弹窗展示算法与指纹 → 管理员显式确认 → 复用现有登记接口完成确认/轮换。交互等同 SSH 客户端首次连接的 yes/no。

## 改动内容

### 后端

- `SshConnectionTester`：新增 `observeHostKey(host, port)`（只握手读取公钥，不比对不登记）；`CapturingHostKeyVerifier` 支持 `expectedFingerprint == null` 观察模式（不构造 FingerprintVerifier、matched 恒 true、仅记录 observation）；新增包内方法 `observedFingerprint()` 供诊断/测试。现有严格模式行为完全不变。
- 新 VO `SshHostKeyObservationVo`：server_id / host_key_algorithm / host_key_fingerprint / **registered_fingerprint**（当前已登记指纹，未确认过为 null，供前端判断密钥是否变更）/ observed_at。
- `ServerSshService.observeHostKey(serverId)`：校验服务器 → 出站策略解析 → `connectionTester.observeHostKey` → 返回 VO（含已登记指纹）。
- `ServerController`：新增 `POST /api/servers/{id}/ssh/host-key/observe`（admin，权限沿用 `/api/servers/*/ssh/**`）。
- 登记仍复用现有 `PUT /api/servers/{id}/ssh/host-key`（CAS 原子写入 + 审计 + 已验证），观察与登记之间若密钥变化会由 PUT 握手比对返回 `SSH_HOST_KEY_MISMATCH`，无 TOCTOU 窗口。
- 测试：`SshConnectionTesterTests`（观察模式 verifier 记录公钥且 matched=true）、`ServerSshServiceTests`（observeHostKey 返回观察结果 + registered 指纹 / 未确认服务器 registered 为 null / 服务器不存在 40400）、`ServerControllerTests`（POST observe 200 / 未认证 40100）。
- OpenAPI 契约：`openapi-server.json` 新增 observe 端点与 `SshHostKeyObservationResult` schema（13 paths / 16 endpoints，`openapi:check` 5/5）。

### 前端

- `src/api/server.ts`：新增 `observeSshHostKey(id)`；`src/types/api.d.ts` 新增 `SshHostKeyObservation` 类型。
- `ServerDetailView.vue`：按钮区新增"一键信任主机"（admin，agentBusy 加载态）→ `trustHostKeyOneClick()`：
  1. `observeSshHostKey` 获取观察结果
  2. 弹窗展示算法 + 指纹；`registered_fingerprint` 与观察指纹不同 → 提示"主机密钥已变更"（replace=true），首次确认 → 提示"确认信任该主机"（replace=false）
  3. 确认 → 复用 `confirmSshHostKey`（PUT）登记 → 成功 toast（confirmed/rotated/unchanged 语义沿用 `operationLabel`）
- 保留原"主机指纹确认"手动输入入口作为带外核对兜底。

## 安全边界说明

- "一键信任"仍要求**管理员显式点击确认**（弹窗展示指纹后才登记），不是 TOFU 自动信任；安全模型从"带外核对指纹"降级为"所见即所信"（管理员信任当前连接目标），对内部学习/demo 项目合理。
- 观察与登记之间若目标密钥变化，复用 PUT 的握手比对会返回 `SSH_HOST_KEY_MISMATCH`，无 TOCTOU 窗口。
- 手动"主机指纹确认"入口保留，需要严格带外核对的场景仍可用。

## 上线后现场修复：云端 SSH_ALLOWED_CIDRS 缺失（2026-08-10 追加）

一键信任上线后云端首次触发真实 SSH 连接，暴露配置缺失：

- **现象**：详情页"一键信任主机"报 `ssh target forbidden`（40301）；后端日志 `Business exception: ssh target forbidden`。
- **根因**：`application.yml` 的 `allowed-cidrs: ${SSH_ALLOWED_CIDRS:}` 默认空；`SshOutboundPolicy.validateAddress` 对空网段列表 `noneMatch` 恒真 → **拒绝一切地址**（含 127.0.0.1）。云端从未设置该变量（此前 wsl111 一直"主机密钥未确认"停留在 409，从未真正发起连接，故未暴露）。
- **修复**：云端 `/etc/susumonitor/server.env` 追加 `SSH_ALLOWED_CIDRS=127.0.0.0/8`（备份 `server.env.bak.20260810`）→ 重启后端。
- **文档**：`docs-SuMon/本机开发环境配置.md` 补充 `SSH_ALLOWED_CIDRS` 必配说明（空 = 拒绝一切，含 40301 排查提示）。
- 注意：前端对 40301 的文案是"目标地址被禁止:仅允许配置的网段"（`explainSshHostKeyError`）；若用户看到"无权限:仅管理员可确认主机指纹"（40300），属 Security 层 AccessDenied，需另行排查（本次日志确认请求已通过 Security 进入业务层，非 40300）。
