## 二、设计权衡记录（不改代码）

1. **report 预算耗尽后当日报告保持 degraded**：调度路径预算耗尽落 degraded(42906) 后，同日手动重试同样被预算检查拒绝（预算不绕过原则），次日恢复。report 预算为独立配置 `AI_REPORT_DAILY_TOKEN_BUDGET` 且默认 0=不限，仅显式配置后才会出现；属预期行为。
2. **报告日期边界为 UTC 口径**：手动生成的"不可晚于当日"以 UTC 为准；+08 用户在本地深夜（UTC 仍是昨天）选"今天"会生成一个窗口尚未结束的报告。与后端/数据层统一 UTC 口径自洽（见下），仅体验边界，不做特殊处理。

## 三、确认无问题的存疑点（取证结论）

1. **时区口径一致**：`metrics.collected_at`（`MetricsServiceImpl.APPLICATION_ZONE=UTC` 归一化写入）、`alert_records.triggered_at`（`AlertEvaluationServiceImpl` 经 `Clock`=systemUTC 写入）、F3 报告窗口（`Clock`=UTC 的 `atStartOfDay`）三者同为 UTC，聚合窗口内部自洽。
2. **聚合 SQL 有索引**：`idx_metrics_collected_at`（V3）支撑日窗口范围扫描。
3. **结果回填幂等**：`completeRun` 带 `status IN ('approved','executing')` 守卫。
4. **安全白名单**：报告 facts 不含 host/IP/凭据；两类通知器独立开关、不耦合告警总开关。

## 四、系统级既有观察（记录在案，本次不处理）

1. **清理 cutoff 与 DB-default created_at 的时区偏差**：`DataCleanupSchedules` 以 UTC 计算 cutoff，但 `alert_records` 等表的 `created_at` 由 DB `DEFAULT CURRENT_TIMESTAMP` 按 MySQL 会话时区写入，保留期存在 ≤8h 偏差（AI 系列表由 Java 写 UTC created_at，不受影响）。建议多实例化/RC1 阶段统一。
2. **多实例下调度重复触发**：`AiHealthReportScheduler` 多实例会重复生成（UPSERT 幂等保证最终一份，但双份 LLM 成本）；单实例 RC1 阶段可接受，多实例阶段需分布式锁（衔接 20260817 多实例计划）。
