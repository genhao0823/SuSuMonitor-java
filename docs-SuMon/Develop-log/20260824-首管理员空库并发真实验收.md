## 一、本轮结论

在**独立空 MySQL schema** 中并发注册投票，两轮均通过：

- **并发 8**：`=== ACCEPTANCE PASS conc=8 ===`
  - DB：`total=8 admin=1 pending=7 invalid=0 bootstrap_init=1 bootstrap_consistent=1`
- **并发 20**（边界）：`=== ACCEPTANCE PASS conc=20 ===`
  - DB：`total=20 admin=1 pending=19 invalid=0 bootstrap_init=1 bootstrap_consistent=1`

两轮均达到模块目标：全部 N 个合法用户名注册成功（HTTP 200 且业务 `code=0`）；恰好 1 个用户为 `admin/approved`，其余 N-1 个为 `user/pending`；管理员可登录且 `GET /api/auth/me` 返回 `admin/approved`；抽样待审核用户登录返回 403；数据库 `auth_bootstrap_state.admin_initialized=1` 且 `initialized_user_id` 指向唯一已审核管理员。隔离 schema 与临时凭据授权在 run 结束后自动清理。

## 二、为什么“修正脚本”而不是改业务

现有验收脚本存在两个与真实业务契约冲突的问题，经用户确认选择修正脚本（而非调整业务规则，也不新增严守“只有一个 HTTP 200”的假命题）：

1. 旧脚本默认用户名前缀 `first-admin-` 含连字符，不符合 `RegisterRequest` 的 `[A-Za-z0-9_]+` 正则校验，脚本一开始就无法通过。
2. 旧脚本以“并发请求中只有一个 HTTP 200”作为成功条件，这与已实现并经单测确认的契约冲突。正确契约：所有不同合法用户名的注册都可成功，只有一个用户成为 `admin/approved`（首个），其余为 `user/pending`。**“成功注册”不等于“获得登录权限”**——待审核用户登录必须被拒绝（403），这是安全边界的关键部分。

## 五、参数与调用链

```text
SUSUMONITOR_VALIDATION_CONCURRENCY (2..20，默认 8；本轮跑 8 与 20)
  -> verify-first-admin-concurrency.mjs 生成 N 个合法 username（<prefix><ts>_<i>）
  -> POST /api/auth/register { username, password }
  -> AuthController.register(RegisterRequest)
  -> UserServiceImpl.register(@Transactional)
  -> auth_bootstrap_state.id=1 SELECT ... FOR UPDATE（AuthBootstrapStateMapper.xml）
  -> UserMapper.insert(UserEntity)：首=admin/approved，其后=user/pending
  -> markAdminInitialized（admin_initialized=0 条件更新，第二层保护）
  -> ApiResponse<CurrentUserVo>
  -> Node 校验 API 状态、角色/审核状态、管理员登录/me、待审核 403
  -> MySQL CLI 复核 users 与 auth_bootstrap_state 最终持久化
```

运行所需凭据只来自运行时环境变量（不写入 `.env`、代码、文档）：

- `DB_PASSWORD`（应用账号口令）
- `SUSUMONITOR_VALIDATION_DB_ADMIN_USER` / `SUSUMONITOR_VALIDATION_DB_ADMIN_PASSWORD`（具备 CREATE/DROP DATABASE 的账号）
- `SUSUMONITOR_VALIDATION_CONCURRENCY`（可选，默认 8）

口令只通过 `MYSQL_PWD` 环境变量传给 `mysql`，不落盘。本日志**不记录任何口令/令牌/数据库名明文**。
