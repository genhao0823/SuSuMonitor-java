# MVP-11 Alert 消费侧实施与验收记录（2026-07-31）

## 一、业务定位

MVP-10 完成 Outbox 发布侧后，`susumonitor.alert.metrics` 队列持续堆积（无消费者）。
MVP-11 = **消费侧落地**：幂等消费 `metrics.reported.v1`，告警评估从本地事务事件
**切换**到消息通道，验收重复投递幂等与 DLQ 分类。

链路（切换后）：Agent 上报 → metrics 落库 + outbox 同事务写入 → 发布器
（1s 轮询）→ `susumonitor.events` → `susumonitor.alert.metrics` →
**AlertMessageConsumer**（幂等检查 + 评估 + 消费记录同事务）→ alert.push / 告警记录。

## 三、关键设计决策

1. **ACK 语义（最终形态）**：AUTO 确认模式 + 业务事务在监听方法内提交后返回
   → 容器在方法返回后 ACK = "业务事务成功才 ACK"。失败不返回 → 不 ACK →
   容器级重试。等价 MVP-10 计划的"MANUAL + afterCommit ACK"，但实现更可靠
   （见 §四踩坑）。
2. **幂等**：`message_consume_records(consumer='alert-evaluator', event_id)` 唯一键；
   消费事务内先 `existsConsumed` 命中则零业务效果；插入与评估同事务，
   ACK 丢失后的重投递由幂等表兜底（"至少一次投递 + 消费幂等"）。
3. **错误分类**（对照冻结契约 §四）：
   - 不可重试（JSON 解析失败 / schema_version≠1 / event_type 不符）：
     `AmqpRejectAndDontRequeueException` → classifier 立即 recover → 容器
     reject(requeue=false) → DLX → DLQ（**零重试**）；
   - 其余异常（DB 临时故障等）：容器级有限重试 3 次（1s/2s/4s 指数退避，
     `ALERT_CONSUME_MAX_ATTEMPTS` 可覆盖）→ 耗尽后容器 reject → DLQ。
4. **条件装配**：`AlertMessageConsumer` + `AlertRabbitConfig` 均
   `@ConditionalOnProperty(susumonitor.rabbitmq.enabled=true)`；test profile
   `enabled=false` 不加载（SystemControllerTests 断言 bean 不存在）。

4. **字段级契约 hardening（后续增量）**：`MetricsReportedMessageValidator` 在幂等查询和
   告警评估前校验 event/message UUID、`producer=metrics-service`、UTC 时间、正
   `server_id`、必填数值、百分比范围、非负量与 used≤total；任一失败统一为
   `AmqpRejectAndDontRequeueException`，保持零重试进 DLQ。此项不引入完整 JSON Schema
   引擎，相关单元测试结果以本次 Maven 回归为准。

## 四、真实验收发现并修复的 Bug（MANUAL ack 踩坑）

**现象**：MANUAL ack 模式下，重试耗尽后消息滞留 unack（不 reject、不进 DLQ），
连接关闭后 requeue 回队列。

**根因链**（spring-amqp 3.2.5 事实）：
- `RejectAndDontRequeueRecoverer`（3.2.x 无 channel 构造）recover 时**只打日志，
  不执行 reject**；
- `ConditionalRejectingErrorHandler` 仅是 `ErrorHandler`（无 channel 引用），
  MANUAL 模式下**容器不替消费者 reject**（手动模式由监听器负责确认）；
- → 重试耗尽后的消息无人 reject，滞留 unack。

**修复**：改用 **AUTO 确认模式**（容器在监听方法返回后 ACK、异常时按错误分类
reject）+ 自定义 `AlertRabbitConfig` 容器工厂：
- `ExceptionClassifierRetryPolicy`：`AmqpRejectAndDontRequeueException`
  （遍历 cause 链）→ `NeverRetryPolicy` 立即 recover；其余 → `SimpleRetryPolicy(3)`
  + `ExponentialBackOffPolicy(1s, ×2, 上限 10s)`；
- 参数仍由 `spring.rabbitmq.listener.simple.retry.*` 驱动（env 可覆盖）。

**验证**：`verify-mvp11.mjs` C3（非法 JSON + schema=2 → DLQ 2 条，重试日志确认
不可重试消息**零重试**立即 reject）。

**延迟说明**：alert.push 增加约 220~800ms，主因是 **outbox 发布轮询间隔

告警场景可接受；如需更低延迟，调小 poll-interval（200-300ms）即可，属 MVP-10
配置调优不在本阶段范围。

## 六、切换策略与留痕

1. 验收库清空 `susumonitor.alert.metrics` 堆积（662 条切换前测试数据）后才启动
   新消费侧，避免旧数据被补消费产生双评估；**生产未部署无存量，无影响**。
2. `MetricsServiceImpl.report()` 保留 `publishEvent(MetricsReportedEvent)`——
   `MonitorMetricsPublisher` 的 `metrics.update` 实时推送仍依赖本地事件；
   仅**告警评估**切到消息通道。
3. 停机影响更新：**告警评估依赖 Broker**——Broker 停机期间指标照常落库（outbox
   堆积），恢复后补发补消费；alert 评估延迟到 Broker 恢复（有界，不丢）。
4. 后续生产性验收资产（2026-07-31 新增，**尚未执行，不得视为 PASS**）：
   - 多消费者并发：`api-test/verify-mvp11-concurrency.mjs`。前置为至少两个连接
     同一验证 MySQL/RabbitMQ 的后端实例；脚本受
     `SUSUMONITOR_VALIDATION_CONFIRM=MVP11_CONCURRENCY` 和本机 Management API
     限制，发布唯一事件及一条并发重复 `event_id`，断言队列回落和业务幂等。
     数据库需按脚本输出的 event_id 额外确认每个消费记录恰为 1 行。
   - DLQ 受控重放：`api-test/replay-mvp11-dlq.mjs`。默认 `dry-run` 使用
     `ack_requeue_true` 只查看有限消息；仅 `--execute` +
     `SUSUMONITOR_VALIDATION_CONFIRM=I_UNDERSTAND_DLQ_REPLAY` 时才以
     `ack_requeue_false` 取出合规 `metrics.reported.v1` 信封，并原样发布回
     `susumonitor.events/metrics.reported.v1`。非法或不兼容死信拒绝重放，且不输出 payload。
   - Broker 停机/恢复：`api-test/verify-mvp11-broker-recovery.md` 规定人工控制
     本机 Broker 的步骤与证据要求：ready 50301、Outbox 堆积、恢复后补发/补消费、
     队列回落以及两个实例的重连日志。脚本不会自动停止或启动 Broker。
