## 一、目标完成情况

告警恢复的完整事件链路（与 `alert.triggered.v1` 全对称）已闭环：

1. **发布侧**：评估器 `handleResolve` 在恢复事务内——`updateStatusToResolved`（V26 起落库 `resolved_at`）→ 同事务登记 Outbox 事件 `alert.resolved.v1` + 发布本地 `AlertResolvedEvent`（AFTER_COMMIT 推 WS）；记录未实际转为 resolved（缺失/已恢复）时不发事件，避免重复恢复语义
2. **WS 推送**：`AlertPushPublisher.onAlertResolved` 向订阅该服务器的 Monitor 会话推 `alert.push` 帧（`payload.alert.status=resolved`，含 `resolved_at`）——前端 `applyAlertPush` 仅递增待刷新计数，**零改动**
3. **消费侧**：新队列 `susumonitor.alert.resolved`（+DLQ），`alert-resolved-notifier` 幂等消费，规则配置了渠道且记录已恢复时排程"恢复通知"（邮件/钉钉/Webhook），复用既有通知退避重试；通知文案按状态区分（`[恢复] ... 已恢复`，不带触发值）

## 三、实现细节与参数传递

### 评估器 handleResolve（`AlertEvaluationServiceImpl`）

```java
LocalDateTime now = LocalDateTime.now(clock);
int updated = recordMapper.updateStatusToResolved(state.getAlertRecordId(), now);
if (updated == 0) {  // 记录未实际转为 resolved（缺失/已恢复）→ 不发恢复事件
    log.warn("alert resolve skipped: record already resolved or missing, recordId={}", ...);
    return;
}
stateMapper.deleteState(state.getId(), state.getVersion());          // 原收口
AlertRecordEntity record = recordMapper.selectRecordById(state.getAlertRecordId());
AlertRecordVo recordVo = toVo(record);                               // status=resolved、resolvedAt 已落库
eventPublisher.publishEvent(new AlertResolvedEvent(record.getServerId(), recordVo)); // AFTER_COMMIT → WS
String eventId = UUID.randomUUID().toString();
String envelope = resolvedEnvelopeFactory.build(recordVo, eventId);  // eventId 与 outbox 行一致
outboxService.enqueue(AlertResolvedEnvelopeFactory.EVENT_TYPE,
        AlertResolvedEnvelopeFactory.ROUTING_KEY, envelope, eventId); // 同事务
```

### 信封契约（message-contracts-v1.md §五）

`event_id / event_type=alert.resolved / schema_version=1 / occurred_at(UTC 秒级) / producer=alert-service / payload{server_id, rule_id, record_id, metric, level, status=resolved, triggered_at, resolved_at}`——**8 字段，不携带触发值**（record.current_value 是触发时刻的值，非恢复语义）。

### 消费者（`AlertResolvedConsumer`，CONSUMER_NAME=alert-resolved-notifier）

- 解析/版本/字段契约不符 → `AmqpRejectAndDontRequeueException` 进 DLQ（容器级有限重试仅对业务异常）
- 幂等：`existsConsumed`（V15）→ 事务内 `dispatchNotifications`（rule 有效且有渠道 && record 存在且 status=resolved → `scheduleNotifications(rule, recordVo)`）+ `insertConsumeRecord` 同提交 → 提交后 `sendScheduled`
- 通知文案：`AlertMessageBuilder` 按 `record.getStatus()` 分支——`[恢复] WARNING cpu 已恢复（阈值 80）` / 正文含触发/恢复时间 / 钉钉 `【SuSuMonitor 恢复】`

## 四、验收发现的缺陷（M5 补修）

真实 broker 验收 C4（失败留痕）暴露：`FailedConsumeRecordRecoverer` 的队列→消费者映射（`QUEUE_CONSUMER`）只含 metrics/triggered 两个队列，**alert.resolved 队列消息失败时留痕回退到缺省 consumer（alert-evaluator）**，且 `extractEventId` 按队列选择信封类型时未覆盖 resolved。已修复：映射补 `AlertResolvedConsumer.QUEUE → alert-resolved-notifier`，`extractEventId` 增加 `isAlertResolvedQueue` 分支按 `AlertResolvedMessage` 解析；新增 2 个单测（10/10）。**教训：新消费者接入必须同步扩展失败留痕 recoverer 的队列映射**（同类风险已在本提交收敛）。
