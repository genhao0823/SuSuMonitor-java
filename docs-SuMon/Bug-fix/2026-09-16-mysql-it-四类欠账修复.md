## 一、为什么欠账沉淀至今

`**/*IT.java` 由 `@EnabledIfEnvironmentVariable(RUN_MYSQL_VALIDATION_TESTS)` 门控 + `TargetDatabaseGuard` 双保险拦截，常规 `mvnw test` 一律 skip。上一次全量复跑是 2026-08-15（19/19，时点基线 550 单测）；此后基线前进至 855 单测当量，V31/V33/V34 迁移、`module/command`、F3 健康报告等能力面先后落地，IT 文件未随代码演进同步——H2 Mapper 单测绿不等于 MySQL 方言行为绿，本专项即为清偿该欠账而设。

## 二、四类根因与修复

### 根因 1：`newRun` 未同步 V33 新增 NOT NULL 审计列（8 Errors）

V33（2026-09-05）给 `ai_command_runs` 补 `risk_level VARCHAR(8) NOT NULL DEFAULT 'low'` 与 `approval_mode VARCHAR(12) NOT NULL DEFAULT 'manual'`；`CommandRunMapper.xml` 的 `insertRun` 显式列出这两列。IT 的 `newRun` helper 未设置对应实体字段 → 显式传 NULL 不触发列 DEFAULT → `Column 'risk_level' cannot be null`。H2 侧 Mapper 单测走 mock/本地 schema 未暴露。

**修复**：`newRun` 补 `setRiskLevel("low")` + `setApprovalMode("manual")`（与 `service_status` L1 low 模板、`manual` source 语义自洽）；顺带在 `insertShouldReturnGeneratedId` 落库断言中补读 `risk_level`/`approval_mode` 两列，把「快照列按实体值落库」纳入验证面。

### 根因 2：ODKU 返回值按 H2 语义断言（1 Failure）

`policyUpsertShouldReplaceSingleRow` 断言 `upsertPolicy(...) == 1`。MySQL `INSERT ... ON DUPLICATE KEY UPDATE` 命中既有行（V33 已种子 id=1）走更新路径，affected rows = **2**；H2 语义返回 1。项目内已有先例——`AiHealthReportMySqlValidationIT.upsertShouldOverwriteSameDateWithoutDuplicates` 的「ODKU 返回值随驱动 useAffectedRows 语义而异，故断言 >=1」注释惯例——command IT 写时未沿用。

**修复**：对齐既有惯例改断言 `>= 1` 并补注释；单行不变量由 `COUNT(*) = 1` 断言兜底（原断言已存在，保留）。

### 根因 3：TINYINT(1) 强转 Number 忽略驱动布尔映射（1 Error + 1 潜伏）

`enabled TINYINT(1)` 在 MySQL Connector/J 默认 `tinyInt1isBit=true` 下由 `queryForMap` 读出 `java.lang.Boolean`；`((Number) seed.get("enabled")).intValue()` 抛 ClassCastException。H2 返回数值故单测绿。两处（`v33ShouldAddRiskColumnsAndPolicyTable` 第 91 行、`policyUpsertShouldReplaceSingleRow` 第 121 行）。

**修复**：新增 `tinyintValue(Object)` 私有 helper（`Boolean → 1/0`，`Number → intValue`），两处改用；不依赖 JDBC URL 参数，驱动两侧语义统一收敛。

### 根因 4：聚合断言与实现语义/自身测试数据矛盾（2 Failures）

- `totalTokensAggregateShouldSumWithinWindow`：断言窗口 `[09-11, 09-12)` 内 sum=0，但 `newEntity` helper（F3 批次为过期清理用例补的）默认 `created_at = 09-11 07:30` **恰在窗口内**——`sumTotalTokensBetween` 按 `created_at` 过滤（XML 第 43-48 行）返回 25 是 SQL 的正确行为，「窗外行不计入」的断言根本没有窗外样本。**修复**：窗外行显式 `createdAt = 09-10 00:00`；补一行窗内样本（`report_date` 唯一键错开一天，`total_tokens = 7`）断言 `sum = 7`——同用例同时验证窗外排除与窗内求和，验证力净增强。
- `aggregationsShouldExcludeSoftDeletedServersAndAggregateCorrectly`：断言 `max_disk_percent = 70.0`（70 恰是**软删服务器** gone-server 的磁盘采样），与同一查询 `JOIN servers s ON s.deleted = 0` 的软删排除语义自相矛盾（CPU 断言 90 已证明排除生效）；实现返回 live-server 的 50.0 正确。**修复**：断言 70.0 → 50.0，注释更正。
