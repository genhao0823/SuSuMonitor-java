## 二、发现并修复的 3 个真实后端 Bug

### 2.1 AlertRecordMapper.insertRecord 缺少 @Param("record")

**文件**：`server-java-SuMon/src/main/java/com/susumonitor/server/module/alert/mapper/AlertRecordMapper.java`

**根因**：`insertRecord(AlertRecordEntity record)` 方法签名未声明 `@Param("record")`，但 XML 使用 `#{record.ruleId}` 前缀引用。与已修复的 `AlertRuleMapper` 500 Bug 完全同类。真实 MySQL 执行时抛出 `ReflectionException: There is no getter for property named 'record'`。

**修复**：方法签名改为 `insertRecord(@Param("record") AlertRecordEntity record)`。

**影响**：告警评估能正确触发（规则匹配、状态查询），但记录插入失败导致评估事务回滚，`alert.push` 永远不发送。单元测试和 H2 Mapper 测试未能发现，因为 H2 MySQL mode 下 MyBatis 参数绑定行为与真实 MySQL 不同。

### 2.2 AlertStateMapper.insertState 缺少 @Param("state")

**文件**：`server-java-SuMon/src/main/java/com/susumonitor/server/module/alert/mapper/AlertStateMapper.java`

**根因**：与 2.1 完全同类的 Bug。`insertState(AlertStateEntity state)` 未声明 `@Param("state")`，XML 使用 `#{state.ruleId}` 前缀。修复 2.1 后，此 Bug 会在首次告警状态插入时暴露。

**修复**：方法签名改为 `insertState(@Param("state") AlertStateEntity state)`。

### 2.3 AlertStateMachine 恢复后再次越界不产生新告警

**文件**：
- `server-java-SuMon/src/main/java/com/susumonitor/server/module/alert/service/AlertStateMachine.java`
- `server-java-SuMon/src/main/java/com/susumonitor/server/module/alert/mapper/AlertStateMapper.java`
- `server-java-SuMon/src/main/resources/mapper/alert/AlertStateMapper.xml`
- `server-java-SuMon/src/main/java/com/susumonitor/server/module/alert/service/AlertEvaluationServiceImpl.java`

**根因**：`AlertStateMachine` 注释设计意图为"RESOLVED → IDLE 恢复后重置（state 被清除后下次评估为 null）"，但 `handleResolve` 只将 state 标记为 `active=0`（inactive），未删除 state 行。恢复后 `selectByRuleAndServer` 返回非 null 的 inactive state，`evaluate` 落入第 59 行 `NoAction` 分支，不产生新告警。

**修复**：
- `AlertStateMapper` 用 `deleteState(id, version)` 替代 `updateStateResolved`，恢复时物理删除 state 行。
- `AlertEvaluationServiceImpl.handleResolve` 改为调用 `deleteState`，使下次评估 `currentState == null`，首次越界逻辑正常工作。
- `AlertStateMachine` 注释更新为"恢复后删除 state 行，下次评估回到 IDLE"。
- 单元测试 `AlertEvaluationServiceTests.recoveryShouldMarkResolved` 的 mock 和 verify 从 `updateStateResolved` 改为 `deleteState`。

**影响**：规划要求"恢复后转为 resolved，再次越界生成新告警"，但实际恢复后再次越界被静默忽略，不产生新告警记录和推送。
