## 一、目标

1. **S2 告警评估性能优化**：`AlertEvaluationServiceImpl` 由"每条规则一次 `selectByRuleAndServer`"（N 次 SQL 往返）改为"每消息一次 `selectByServerId` 批量查状态 + 内存 Map 分发"（2 次 SQL 往返），消除 100 规则场景的 +45ms 查询放大。
2. **通知总开关语义修复**：`notificationEnabled` 从"只约束 email"改为真正约束全部外部渠道（email/dingtalk/webhook），与字段注释语义一致。

**技术栈**：全复用——MyBatis XML 单查询（走 V10 已有 `idx_alert_states_server` 索引）、Java Stream `Collectors.toMap`、JUnit5/Mockito/H2、既有 `bench-alert-chain.mjs`。**零新依赖、零表结构变更、零 API 契约变更**（openapi:check 不受影响）。

## 三、实现细节与参数传递

### 模块 A：S2 评估性能优化（M2）
- `mapper/AlertStateMapper.java`：新增 `List<AlertStateEntity> selectByServerId(@Param("serverId") Long serverId)`；删除 `selectByRuleAndServer`（唯一生产调用点即评估器，grep 确认后删除不留死代码）。
- `resources/mapper/alert/AlertStateMapper.xml`：新增 `<select id="selectByServerId" resultMap="AlertStateResultMap">SELECT <include refid="StateColumns"/> FROM alert_states WHERE server_id = #{serverId}</select>`；删除旧 select。全局规则（`server_id IS NULL`）状态行按上报 server 落库，同样被覆盖。
- `service/AlertEvaluationServiceImpl.evaluate(metrics)`：
  - rules 为空仍提前返回；
  - 随后**一次** `selectByServerId(metrics.getServerId())`，`Collectors.toMap(AlertStateEntity::getRuleId, state -> state, (first, ignored) -> first)` 建 `Map<Long, AlertStateEntity> statesByRule`（uk_alert_states_rule_server 唯一键保证无重复，merge 纯防御）；
  - 循环内改为 `evaluateRule(rule, metrics, statesByRule.get(rule.getId()))`。
- `evaluateRule(AlertRuleEntity rule, MetricsLatestVo metrics, AlertStateEntity state)`：签名新增 state 形参；`stateMachine.evaluate(rule, metrics, state)` 与全部 `handle*` 不变。
- 语义变化（诚实声明）：批量读失败抛出 → `AlertMessageConsumer` 容器重试整条消息（旧行为：单规则读失败记 warn 继续其余规则）；每规则评估/写入失败的 try/catch 隔离保留。
