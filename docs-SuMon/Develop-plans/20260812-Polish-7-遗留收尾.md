## 四、各模块代码细节

### M2 SSH 测试历史保留期清理（技术栈：Java 21 / Spring Boot 3.4.7 / MyBatis-Plus / Flyway / @Scheduled）

- 新建 `db/migration/V24__add_ssh_test_history_retention_index.sql`：
  `ALTER TABLE ssh_test_history ADD INDEX idx_ssh_test_history_tested_at (tested_at);`
  （V23 的 `(server_id, tested_at)` 复合索引不满足 tested_at 单独范围扫描）
- `SshTestHistoryMapper` + XML 新增：`int deleteOlderThan(@Param("cutoff") LocalDateTime cutoff, @Param("limit") int)`
  → 分批 `DELETE FROM ssh_test_history WHERE tested_at < #{cutoff} ORDER BY tested_at LIMIT #{limit}`
- 新建 `module/server/service/SshTestHistoryCleanupService`（仿 `AlertRecordCleanupService`）：
  - cutoff = now - retentionDays（UTC）；循环批量删 ≤ maxBatchesPerRun
  - 返回 `CleanupResult(cutoffTime, batchCount, deletedRows)`；运行互斥沿用现有模式
- 新建 `scheduler/SshTestHistoryCleanupScheduler`（仿 `AlertRecordCleanupScheduler`）：
  `@Scheduled(cron = "${susumonitor.ssh-test-history.cleanup-cron}")` + `@ConditionalOnProperty(name = "susumonitor.ssh-test-history.cleanup-enabled", havingValue = "true")`；异常只影响本轮
- `application.yml`（local/prod 同步）新键（沿用 `${ENV:default}` 风格）：
  - `susumonitor.ssh-test-history.retention-days: ${SSH_TEST_HISTORY_RETENTION_DAYS:90}`
  - `susumonitor.ssh-test-history.cleanup-cron: ${SSH_TEST_HISTORY_CLEANUP_CRON:0 0 3 * * ?}`
  - `susumonitor.ssh-test-history.cleanup-enabled: ${SSH_TEST_HISTORY_CLEANUP_ENABLED:true}`
  - `susumonitor.ssh-test-history.cleanup-batch-size: ${SSH_TEST_HISTORY_CLEANUP_BATCH_SIZE:1000}`
  - `susumonitor.ssh-test-history.cleanup-max-batches-per-run: ${SSH_TEST_HISTORY_CLEANUP_MAX_BATCHES_PER_RUN:100}`
- 测试：`SshTestHistoryCleanupServiceTests`（Mockito：cutoff 计算/分批循环/空数据 0 批）+ Mapper Mybatis 测试补 deleteOlderThan 用例
- 备份：application.yml（local/prod）→ `local/backup-polish7/m2/`

### M3 Android 自研 ANSI 终端模拟器（技术栈：Kotlin 2.0.21 / Compose / 纯 JVM 单测）

- 新建 `ui/terminal/TerminalEmulator.kt`（纯 Kotlin 无 Android 依赖，JVM 可测）：
  - `Cell`（ch / foreground / background / bold）；`Screen` = rows×cols 网格 + scrollback `ArrayDeque`；primary/alt 双屏；cursor(row, col, visible)；savedCursor；scrollRegion；wrapPending；modeFlags（?1049 alt、?25 光标）
  - `TerminalParser` 增量状态机：ESC / CSI（`ESC[ 参数 终结符`）/ OSC（忽略至 BEL/ST）/ 单字符控制（BS/TAB/LF/CR/BEL）

### M5 Agent metrics.nack 有限重试（技术栈：Go 1.23 / coder/websocket）

- Server：`MetricsRejectionReason` 新增 `RETRIABLE_SERVER_ERROR("retriable_server_error")`；`MetricsServiceImpl` 入库路径捕获可恢复异常（DataAccessException 等）→ 抛 `MetricsRejectedException(RETRIABLE_SERVER_ERROR)`；WS 层 nack 载荷自动带 reason
- Agent 协议：`wsclient.MetricsNack` 不变（按 reason 分级，向后兼容）
- `metricbuffer`：queue entry 增加 `NackCount`（snapshot v3 + v2→v3 迁移，沿用现有 v1→v2 迁移模式）；新方法 `RejectOrRetryHead(messageID, nack, maxRetries)`：retriable_server_error 且 NackCount < maxRetries → 回队尾 + NackCount++（持久化）；否则死信（现状）
- `reporter.HandleMetricsNack` 改走分级逻辑，重试调度复用现有 retryTimer 退避
- 配置 env（config 严格校验 + .env.example + README）：`SUSUMONITOR_NACK_RETRY_MAX`(默认 3)、`SUSUMONITOR_NACK_RETRY_INITIAL`(默认 2s)、`SUSUMONITOR_NACK_RETRY_MAX`(默认 60s)
- 设计留痕：stale_collected_at / invalid_metrics_payload / server_not_found 维持永久死信（重发不改变拒绝条件，文档写明理由）
- 测试：metricbuffer（v3 迁移、NackCount 持久化）+ reporter_test 扩展（重试路径/上限转死信/永久原因直接死信）
- 备份：reporter.go、buffer.go 等 → `local/backup-polish7/m5/`
