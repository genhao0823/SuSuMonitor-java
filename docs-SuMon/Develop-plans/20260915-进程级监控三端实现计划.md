# 进程级监控（Top Processes）三端实现计划

- **日期**：2026-09-15
- **前置**：20260914 全功能前后端联调收口后的进度盘点确认——全系统无进程级监控（Agent 只采 CPU/内存/单盘/网络，`gopsutil_collector.go` 的 `diskUsage` 仅取 `systemDiskPath()` 单路径），属规划外能力缺口中价值最大的新业务面。

## 一、目标

三端打通「实时 Top 进程」：Agent 采集 → 后端转发 → 前端展示。每服务器每采集周期（默认 5s）上报 CPU 占用与内存占用两个 Top N 排行。

## 二、口径决策（本次已拍板）

1. **实时快照，不入库**——进程是列表型易变数据，不进 metrics 宽表、不建新表；后端内存保留每服务器最新快照（TTL 90s），REST 提供最近一次快照，WS 随 metrics.update 实时捎带。历史持久化如需再立专项（分区表）。
2. **只读，不提供 kill/终止操作**——若将来需要，应挂到 command 模块审批制下，不并入本次。
3. **向后兼容**——Jackson 已确认忽略未知字段（Spring Boot 默认，全仓无 FAIL_ON_UNKNOWN_PROPERTIES 全局开启）；旧版 Agent 不带进程字段时一切照旧，前端显示空态。
4. **字段最小化**——只上报 pid、进程名、CPU%、内存占比；不采 cmdline/env（避免敏感泄露与载荷膨胀）。

## 三、数据流设计

```
Agent(每5s采集周期): 扫描进程表 → CPU% 用 /proc 时间片差分(不阻塞) → 取 CPU Top10 + 内存 Top10
  → metrics.report payload 新增可选字段 process_cpu_top / process_mem_top（离线缓冲同结构重放，无害）
后端: MetricsReportPayload 新增可选字段（校验：列表≤20、名称≤128字符、数值0-100）
  → 内存注册表 ProcessSnapshotRegistry 更新（Clock 可注入，TTL 90s 判过期）
  → MetricsReportedEvent 捎带快照 → MonitorMetricsPublisher 在 metrics.update payload 加可选 processes 节点
  → 新 REST: GET /api/servers/{id}/processes/latest（404=无快照或已过期）
前端: MetricsView 新增「实时进程」卡片（CPU/内存两个 Tab 的 el-table）
  → 进页先 REST 取快照（404 显示空态），之后 WS metrics.update 覆盖刷新
```

WS 帧数不增加（捎带在既有 metrics.update 里）；协议文档 websocket-protocol.md v1.3 → v1.4 仅追加可选字段说明。

## 六、风险与对策

- **容器内进程采集**：容器里 gopsutil 只见本命名空间进程——联调如实验证并文档注明
- **短命进程/pid 复用**：差分基线倒退即重置，防畸高 CPU
- **载荷膨胀**：Top10×2 每帧 <1KB；校验层兜底 20 条上限
