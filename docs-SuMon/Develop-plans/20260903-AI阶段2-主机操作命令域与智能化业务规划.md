## 一、背景与目标

MVP 阶段确立了三块可复用资产：

1. **供应商无关端口**：`AiProvider`（`module/ai/provider`）——固定 provider、HTTPS 默认、结构化输出严格校验、有界重试、确定性降级。
2. **只读上下文链路**：白名单组装（`ServerStatusVo`/`MetricsLatestVo`/告警摘要，不含 SSH 字段与告警文本）、反伪造 evidence、V28 审计与清理。
3. **治理基建**：按管理员限流、按天 token 预算、kill switch（`AI_ENABLED` 默认关闭、关闭零触达）、错误码段（42906/50303/50304/50305/50401）。

本阶段目标分两类：

- **只读智能化三件套**（不动安全边界，直接增量）：
  - **F1 告警智能解释**：告警触发后自动生成原因分析/影响/排查建议，随通知渠道推送。
  - **F2 运维问答工具化**：管理员自然语言提问，模型经只读工具注册表自主取数后回答。
  - **F3 定时健康报告**：周期性汇总全量服务器状态、趋势与告警统计，生成可读报告并推送。
- **AI 主机操作命令域**（**F4，本阶段核心体量**）：AI 能够对目标主机执行受限命令——分析后给出建议命令，经审批或分级授权后由 Go Agent 受限执行器执行，结果回传 AI 解读。这是既有威胁模型 §九 禁令的**受控解禁**：走独立协议、独立审批、独立审计，而非放宽只读端点。三种交互模式（M1 审批制 / M2 风险分级 / M3 AI 自审批）分阶段启用，见 §三 F4。

**F5 后续候选（不入本阶段）**：RAG 运维知识库（前置：文档源确认 + 向量库选型）、会话式排障（前置：会话记忆与存储/保留策略）。仅记录候选与前置条件，不展开。

## 二、非目标（安全边界声明）

- **不放宽、不复用只读诊断端点**做任何执行；`/api/ai/diagnoses` 保持只读语义。
- **模型永不接触 `terminal.*` PTY**。现有 Web 终端通道保持 admin 人工专用，不接入 AI；协议文档中"AI 永不直接使用终端帧"的表述继续有效。命令域走独立的 `command.*` 通道（见 §三 F4）。
- **SSH 凭据永不出现在 prompt、模型上下文、日志或命令参数中**。命令域经 Go Agent 受限执行器执行，Java/模型均不新建 SSH 会话、不解密凭据。
- **模型只能引用命令模板 ID，不能生成任意命令字符串**（详见 F4.3）。任何 shell 元字符注入、模板外命令一律拒绝。
- **本阶段不做 RAG、不做向量库、不做会话记忆**（F5 候选另立）。
- **M3（AI 自审批）仅定义启用门禁，不承诺实现时间**；启用需产品/安全责任人书面风险接受，默认关闭。
- 文档完成 ≠ 实现完成 ≠ 测试通过 ≠ 真实环境验收；各阶段独立验收。
- 不复用 V4 孤儿 `commands` 表（语义过时且无业务接线，RC1 计划已声明"无产品需求不接入"；本阶段建新表）。

## 三、业务功能清单

### F1 告警智能解释

- **用户故事**：管理员收到告警通知时，除阈值事实外还能看到一段分析——可能原因、影响判断、建议的人工排查步骤（非执行指令）。
- **触发链路**：`alert.triggered.v1` 消费链路（现有 `AlertTriggeredConsumer`）→ 发起 AI 解释请求 → 异步 LLM 调用 → 结果存储（关联 alert_record）并随邮件/钉钉/Webhook 通知推送 → 前端告警详情可回看。
- **选型结论**：**扩展现有 `AiProvider` 端口，不引 Spring AI**。理由：单次白名单上下文 → 单次结构化 JSON 返回，MVP 链路已实战验证（含降级/审计/限流），框架收益为零。
- **异步化**：新增独立版本化事件 `ai.alert.explanation.requested.v1`（Outbox + Rabbit topic + 独立队列 + DLQ + 消费幂等，全部复用 MVP-10/11 模式），**不复用** metrics/alert 事件语义。解释失败不阻塞告警本身，通知中降级为无解释原文。
- **依赖**：现有告警链路、`AiProvider` 端口、通知渠道；无新安全前置。

### F2 运维问答工具化

- **用户故事**：管理员提问"昨晚 3 点之后哪台服务器 CPU 超过 90%？分别现在什么状态？"——模型自主决定调用哪些只读工具（最新指标/历史指标/告警记录/服务器状态/只读命令结果），取数后组织带证据的回答。
- **选型结论**：**引入 Spring AI（ChatClient + Function Calling），实现为 `AiProvider` 端口的第二个实现 `SpringAiProvider`**。理由：多轮 tool-loop（模型调工具 → 取结果 → 再推理）自研成本明显高于框架收益；Spring AI 要求 Spring Boot 3.2+/Java 17+，当前 3.4.13/Java 21 兼容。这是**本阶段唯一新增框架依赖**，遵守：
  - 版本锁定：具体版本在阶段 B 开工前评审定稿（见 §九 开放项），升级视为独立变更。
  - 依赖隔离：Spring AI 相关代码收敛在 `module/ai` 内，不向 metrics/alert/server 等模块扩散；`AiProvider` 端口契约不变，可随时回退到 `OpenAiCompatibleProvider`。
  - 工具白名单：注册表只含只读工具，全部经现有 Service 契约（`MetricsService`/`AlertRecordService`/`ServerService`）取数，模型不接触 Mapper/SQL；每个工具调用记审计（工具名、参数摘要、耗时）。
- **回答边界**：沿用 MVP 反伪造原则——事实字段（指标值、告警记录、命令结果）由工具返回并作为 evidence 呈现，模型只负责解释；工具未覆盖的问题如实说"数据不足"。
- **依赖**：Spring AI 选型评审；F4-M1 完成后可把"只读命令执行"注册为工具（前置依赖 M1）。

### F3 定时健康报告

- **用户故事**：管理员每天早上收到一页报告——全量服务器在线率、指标趋势摘要、昨日告警统计、Agent 掉线记录，附"值得关注的三件事"。
- **触发链路**：Scheduler（复用现有调度模式与 `@ConditionalOnProperty` 惯例）→ 汇总只读数据（同 MVP 白名单口径）→ 单次 LLM 摘要 → 报告落库（新表，见 §五）→ 推送通知渠道 → 前端可查历史报告。
- **选型结论**：现有 `AiProvider` 端口扩展（单次调用）；事件与消费基建复用 F1 新增的模式。
- **依赖**：F1 的异步事件基建（共享队列模式与报告/解释存储设计）。

### F4 主机操作命令域（核心）

#### F4.1 三种交互模式（已定，分阶段启用）

| 模式 | 行为 | 启用条件 |
|---|---|---|
| **M1 审批制** | AI 生成"命令模板 ID + 类型化参数 + 理由"，前端预览，管理员逐条审批，Agent 执行，结果回传 AI 解读 | 阶段 D 首批实现；默认关闭，随 `AI_COMMAND_ENABLED` 独立开关 |
| **M2 风险分级** | 低风险命令 AI 自主执行（事后通知+审计），中高风险仍走审批 | 依赖命令风险分级体系上线 **且 M1 审计数据积累达到评审基线**（观察期时长见开放项）；默认关闭 |
| **M3 AI 自审批** | AI 自行判断并执行，无逐条人工审批 | **高风险模式，本阶段仅定义门禁不承诺实现**：M2 稳定运行观察期 + 审计窗口内零 critical 安全事件 + 按服务器范围授权生效 + 独立 kill switch + 默认关闭 + 产品/安全责任人书面风险接受。任一条件不满足即不得启用 |

三模式共用同一套命令模板白名单、执行通道、审计与脱敏；差异仅在"谁来批准"。

#### F4.2 执行通道（已定：Agent 受限命令通道）

- Go Agent 新增**受限命令执行器**：非 PTY、逐命令独立进程（`exec.CommandContext`）、强制超时、输出字节上限、输出脱敏（凭据/token 模式扫描，命中即截断替换）、退出码与耗时回传。不提供交互式会话，不提供 shell。
- Java 经已认证的 Agent WebSocket 下发新消息 **`command.execute` / `command.result`**——对齐《项目需求与规范》WebSocket 章节早已预留的增强消息类型。协议细节（字段、幂等、限流、超时、错误码）在阶段 D 冻结独立契约文档（沿 `message-contracts` 惯例），不复用 metrics/alert 事件。
- 路由与归属校验复用现有 Agent 通道安全模型：`server_id` 归属已认证 Agent 连接、消息限流（独立于 terminal/metrics 令牌桶）、Agent 离线时拒绝并回写审计。
- **AI 不持有 shell**：模型输出到执行器的唯一合法输入是"模板 ID + 参数"，其余一律拒绝（见 F4.3）。

#### F4.3 命令白名单与风险分级（已定起点：只读先行）

分级与晋级流程（晋级 = 阶段出口评审通过后写入白名单配置，逐级放开）：

| 级别 | 示例（首批只读清单） | 说明 |
|---|---|---|
| **L1 只读（首批）** | `systemctl status <unit>`、`df -h`、`free -m`、`uptime`、`ss -tlnp`、`journalctl -u <unit> -n <lines>`、`top -b -n1`、`ps aux` | 无副作用；M1 审批制验证全链路 |
| **L2 低风险变更（M2 起）** | 日志轮转/清理类、`systemctl reload` | AI 可自主执行，事后通知+审计 |
| **L3 高风险变更（M2 仍审批）** | `systemctl restart <unit>`、进程终止 | 仅审批制；M3 门禁评审后才可能纳入自主范围 |

**关键约束（prompt injection 的命令面防线）**：模型只能输出**白名单模板 ID + 类型化参数**；模板定义参数 schema（名称/类型/正则/取值范围），Java 侧做模板匹配 + 参数校验，任意命令字符串、shell 元字符、管道/重定向、模板外拼接**一律拒绝**并记审计。参数进执行器前再经 Go 侧二次校验（纵深防御）。

> **2026-09-10 实现注**：自动审批首版的风险分级落表为 `risk_level ∈ {low, medium, high}`（`CommandRiskLevel` 枚举，当前 8 个 L1 模板全部标 low）；策略阈值仅接受 `low | medium`，HIGH 永不自动审批；自动审批只作用于 AI 来源（`source='ai'`）的建议命令。与本节 L2/L3 变更类分级的差异：L2/L3 尚未进入白名单，属后续阶段。

#### F4.4 持久化（V29+，不复用 V4）

- `ai_command_runs`：执行审计——发起人、目标服务器、模板 ID、参数 hash（不存原文参数之外的自由文本）、状态（pending_approval/approved/executing/succeeded/failed/rejected/expired/timeout）、审批人、退出码、耗时、**脱敏截断后的输出 result_json（默认 64KB 上限，随保留期清理；2026-09-04 实现时按用户决策由"仅存 hash"调整为落库脱敏截断输出，以便审计回查）**、请求/关联 ID、时间戳。
- `ai_command_approvals`：审批记录——审批人、时间、过期时间（超时未审批自动过期）、结果、理由。（M1 实现简化：审批人/时间/结果直接落 `ai_command_runs` 行，独立审批表推迟到多人审批策略引入时再建。）
- 输出原文在 Go 侧脱敏+截断后落库；审计保留期（默认 30 天）与清理沿用现有 Scheduler 模式。
- 命令模板与分级以**服务端配置/代码常量**为准（版本化），管理员不可经 API 动态增删模板。

#### F4.5 权限与治理

- API 与业务双 admin 校验；"按服务器范围授权"模型列为开放项（首批全 admin 可用）。
- 独立 kill switch：`AI_COMMAND_ENABLED`（默认 false），与只读诊断 `AI_ENABLED` 互不影响；关闭时命令端点/WS 消息全部拒绝。
- F2/F1 的限流与按天预算延伸覆盖命令调用（命令场景单独配额）。
- 前端审批 UI（预览/审批/历史）为 Web 工作项，是阶段 D 的外部依赖（见 §七）。
- 阶段 D 交付时新增命令域专属威胁模型文档 `ai-command-domain-threat-model.md`，并同步更新现有 `ai-data-flow-threat-model.md` §九（解禁范围以命令域文档为准）。

## 四、技术选型总表

| 功能 | 选型 | 理由 |
|---|---|---|
| F1 告警解释 | 现有 `AiProvider` 端口扩展 | 单次结构化调用，MVP 链路已验证，框架零收益 |
| F2 问答工具化 | **Spring AI ChatClient + Function Calling**（`SpringAiProvider` 实现端口） | tool-loop 自研成本高于收益；端口保持可替换、依赖隔离、版本锁定 |
| F3 健康报告 | 现有 `AiProvider` 端口扩展 | 同 F1 |
| F4 命令域 | 现有端口（生成模板调用）+ Go Agent 受限执行器 + 新 `command.*` 协议 | 执行安全性由模板白名单+审批+审计保证，与框架无关 |

**为何不全量上 Spring AI**：MVP 端口已承载 fail-closed（HTTPS-only/白名单/反伪造/严格枚举/降级）等自研安全语义，全量迁移需重新验证全部安全行为；Spring AI 的明确收益点当前只有 tool-loop（F2），按需引入、最小面暴露。

## 八、验收门槛

通用三态口径：**实现完成 ≠ 自动化测试通过 ≠ 真实环境验收**；各阶段独立记录，不互相借用 PASS。

- **F1/F3**：解释/报告内容含证据引用与 limitations；provider 失败降级不阻塞告警/报告主链路；事件消费幂等可重放；审计与保留期清理可验证。
- **F2**：工具调用全部白名单命中且有审计；注入 fixture（问题中夹带"执行/终端/凭据"指令）不改变系统约束；预算耗尽拒绝；可回退 `OpenAiCompatibleProvider`。
- **F4-M1（安全重点）**：模板外命令、shell 元字符、参数越界**全部拒绝且留审计**；越权服务器/非 admin 拒绝；审批过期/取消/重复审批语义正确；Agent 离线不悬挂；输出脱敏验证（凭据样式内容不回传不落库）；kill switch 全链路生效；Go 侧二次校验独立于 Java 校验成立；真实 Agent E2E（执行/超时/输出截断/离线）通过。
- **F4-M2**：低风险自主执行有事后通知与审计；中高风险无法绕过审批（含并发与重放场景）。
- **F4-M3**：仅评审文档与决策记录，满足 §三 F4.1 门禁清单才可进入后续实现立项。
