## 一、目标

1. **阶段 C / F3 定时健康报告**：管理员每天早上收到一页报告——全量服务器在线率、指标趋势摘要、昨日告警统计、离线服务器清单，附"值得关注的三件事"（20260903 计划原文用户故事）。链路：Scheduler（条件装配）→ 汇总只读数据（白名单口径）→ 单次 LLM 摘要 → 报告落库（新表 V34）→ 推送通知渠道 → 管理员历史查询 API。
2. **阶段 E 遗留 / 自动审批事后通知**：策略自动审批（`approval_mode='auto'`）的命令运行在结果回填（succeeded/failed/timeout）后推送一条尽力而为的通知（邮件/钉钉/Webhook），补上"当前仅审计标识可查，无通知推送"的缺口。

## 二、关键设计决策

| 决策点 | 结论 | 理由 |
| --- | --- | --- |
| 触发链路 | Scheduler 直接调用 Service（不经 Outbox/RabbitMQ） | 触发方是服务端自身调度而非外部事件；单次幂等生成（report_date 唯一键）无重放需求，绕开事件链路可少一对队列/DLQ 的运维负担；与 20260903 计划"复用现有调度模式与 `@ConditionalOnProperty` 惯例"一致 |
| report_date 语义 | 报告内容覆盖"被汇总的自然日"（调度在次日早上生成昨日报告） | 用户故事是"每天早上收到昨日报告"；手动触发可指定任意历史日期（重生成走 UPSERT） |
| provider 失败 | 降级不阻塞：报告仍落库（`status=degraded`，聚合事实保留，`summary` 为空，`error_code` 记录原因） | 20260903 §八 验收门槛"provider 失败降级不阻塞报告主链路" |
| 数据口径 | 离线清单为**当前快照**（servers.status + last_heartbeat_at），报告 limitations 中注明无独立掉线事件流水 | 现有表无 Agent 掉线事件流水；指标汇总按 metrics.collected_at 窗口聚合并 JOIN servers 排除软删 |
| 通知渠道 | 报告与命令通知均为**配置级**渠道（`notify-email/webhook/dingtalk`），不复用按规则配置的告警渠道 | 健康报告/命令通知不属于任何告警规则；不耦合 `alert.notification-enabled` 总开关，各自带独立 `notify-enabled` |
| 通知语义 | 尽力而为（best-effort）：不落库、不重试、异常只记日志 | 与 `AiAlertExplanationNotifier` 同一语义；报告/审计行本身已可回看 |
| 白名单 | 报告事实不含 host/IP/SSH/凭据/通知渠道，仅 server_id、名称、状态、聚合值 | 与 `AiDiagnosisContext` 反伪造口径一致 |
