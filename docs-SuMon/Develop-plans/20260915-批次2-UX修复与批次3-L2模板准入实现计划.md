1. **B2-1 根因链完整确认**：`src/api/client.ts` 的响应拦截器在 `handleBusinessError` 中对非 silent 请求弹 `ElMessage.error`，而 `LoginView.vue` 的 `handleSubmit` catch 分支又弹一次——失败一次出现两条提示。**且错误密码（HTTP 401/40001）会触发 `onUnauthorized` 回调、待审核账户（HTTP 403/40300）会触发 `onForbidden` 回调把用户从登录页推向 `/forbidden`**——登录尝试失败被误判为"会话失效/权限不足"。修复面因此扩为：静默弹窗 + 跳过登录态回调（详见 §二 B2-1）。

## 二、批次 2：联调观察项 UX 修复（前端 only）

### 2.1 B2-1 登录失败单提示 + 不误触全局登录态回调

**决策（本次拍板）**：不沿用"仅 `silent: true`"的最小修法，增加独立的 `authAttempt` 配置位。理由：`silent` 现有语义是"跳过弹窗、回调仍触发"（既有调用方依赖回调语义），若让 `silent` 连带跳过回调会改变全部既有 silent 请求的行为；登录尝试失败（401/403/429）语义上是"这次尝试被拒"，不是"会话失效/权限不足"，用独立标记表达，影响面精确为零（仅 login 一处使用）。

代码改动（3 个文件）：

- `src/api/client.ts`：
  - `AxiosRequestConfig` 扩展接口追加 `authAttempt?: boolean`，注释说明：标记请求为"认证尝试"，40100/40300 表示本次尝试被拒而非登录态变化，跳过全局回调。
  - `handleBusinessError` 签名改为 `(code: number, message: string, config?: { silent?: boolean; authAttempt?: boolean })`；回调分支包裹 `config?.authAttempt !== true` 判断；弹窗分支保持 `config?.silent !== true`。两个调用点改为传 `response.config` / `error.config` 整体。
  - 顶部接口 docstring 同步更新（回调触发条件增加 authAttempt 例外）。
- `src/api/auth.ts` `loginUser`：POST 第三个参数传 `{ silent: true, authAttempt: true }`；注释说明"登录失败的文案与跳转由 LoginView 统一处理，全局拦截器不弹窗、不触发登录态回调"。
- `src/views/LoginView.vue`：**零改动**——它已是单一文案来源（`explainLoginError` 映射 40300/40001/40002）。

新增测试：

- `src/api/auth.spec.ts`（新建，对齐 `ai-settings.spec.ts` 的 spy 模式）：
  - `loginUser 调 POST /auth/login 并携带 silent+authAttempt`：`vi.spyOn(apiClient, 'post')`，断言 `toHaveBeenCalledWith('/auth/login', body, { silent: true, authAttempt: true })`。
  - `registerUser/logoutUser/getCurrentUser` 既有形态断言（顺带补齐该文件空白，防止后续漂移）。
- `src/api/client.spec.ts`（新建）：通过 `apiClient.defaults.adapter` 注入伪 401/403 响应（AxiosError 构造带 `response.status` 与 `data.code`）：
  - 携带 `authAttempt: true` 的请求：`setApiClientCallbacks` 注册的 `onUnauthorized`/`onForbidden` 均不触发，且无 `ElMessage.error`；
  - 未携带 authAttempt 的请求：回调触发、非 silent 时弹窗一次（守卫既有语义不被本次改动破坏）；
  - `vi.mock('element-plus')` 局部替换 `ElMessage` 为 spy 对象。
- `src/views/LoginView.spec.ts`（新建）：
  - mock `@/api/auth`（`loginUser` reject `ApiBusinessError(40001)`）、mock `vue-router`（`useRoute` 返回 `{ query: {} }`、`useRouter.push` 为 spy）、stub `AuthLayout` 透传 slot、stub `RouterLink`；
  - 断言失败提交后 `ElMessage.error` **恰好调用 1 次**且文案为"用户名或密码错误"；
  - 断言 `loginUser` 被以正确 body 调用（token 提交路径不回归）；

## 三、批次 3：L2 变更类模板准入（协议 + Agent + Java）

### 3.1 模板定稿（与 M2 计划冻结值一致）

| id | argv | 风险 | 参数正则 |
|---|---|---|---|
| `systemctl_reload` | `systemctl reload {unit}` | medium | `unit`: `^[a-zA-Z0-9@._-]{1,64}$` |
| `journalctl_vacuum` | `journalctl --vacuum-time={days}d` | medium | `days`: `^[1-9][0-9]{0,2}$`（1-999 天） |

`systemctl_reload` 的 unit 正则比 L1 `UNIT_PATTERN`（128 长、含 `:`）更紧（64 长、不含 `:`）：reload 目标是常驻服务单元而非 device/scope 类单元，收紧不损失业务表达，且变更类入口从严。

### 3.2 决策（本次拍板）

- **D3-1 替换语义统一为子串替换**：Go `replaceArgv` 从"整元素相等才替换"改为 `strings.ReplaceAll(part, placeholder, value)`。安全性论证：value 在替换前已通过白名单正则**完整匹配**校验（拒绝元字符/空白/分号），子串替换不会引入 argv 切分或 shell 注入面；替换后仍是一个 argv 元素，不二次拆分。Java 侧本就是子串替换，统一后双侧渲染结果逐字一致，人工预览=真实执行的语义可断言。
- **D3-2 Go 侧不引入 risk 字段**：风险分级是 Java 侧审批策略概念，Agent 职责是"模板白名单 + 参数校验 + 受控执行"，与 L1 时代一致，避免双侧冗余口径。
- **D3-3 默认策略不动**：`CommandAutoApprovalPolicyService` 默认 `enabled=0` 保持；medium 模板入库后是否放开自动审批由管理员依据批次 1 观察报告决策（产品语义，不代码化）。
- **D3-4 协议先行**：`command-protocol-v1.md` §五扩为"L1 只读 + L2 变更类"双层模板表并加修订记录，随后双侧实现同批对齐；openapi-command.json 若模板清单仅在 examples 出现则同步示例，`npm run openapi:check` 必须全绿。
